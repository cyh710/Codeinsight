## 一句话

让 Agent **持续维护**对一个真实仓库的认知——符号、调用关系、**技术概念**、版本演进、设计说明——
并把这份认知同时用于问答、变更解释与原理讲解。

系统以**理解为主线，开发为辅助，学习按需展开**：CodeInsight 负责"读懂并讲清楚"，
实际的代码修改交给外部 agent（Claude Code / Codex 等）经 **MCP Server** 调用本系统的理解能力。

### 检索层的验收数字（M2）

题目从索引**自动生成**（ground truth = 那个符号的 `file:line`），不手工标，
所以数字可复现、可回归：

同一批题（seed 固定、索引不变），只改通道开关：

| 题型 | 通道 | 命中 | MRR | Top-1 |
|---|---|---|---|---|
| `name` | bm25 + symbol + concept | 10/10 | 0.750 | 50% |
| `name` | **+ dense**（bge-m3） | 10/10 | **0.850** | **70%** |
| `docstring` | bm25 + symbol + concept | 10/10 | 0.700 | 50% |
| `docstring` | **+ dense**（bge-m3） | 10/10 | **0.900** | **80%** |

`docstring` 题型靠「符号名精确匹配」是答不上的——它才是真正区分
「关键词检索」和「结构化检索」的地方，也是稠密通道贡献最大的地方
（MRR +0.20）。

> n=10 的样本，MRR 差 0.1 只相当于名次挪一格，**不要把它当结论**；
> M5 会把 n 拉到几十并给出 95% CI。

四路通道都实现并可单独开关：`bm25` / `dense` / `symbol` / `concept`。
**通道开关就是评测的臂**（`none` / `bm25` / `hybrid` / `symbol` / `concept`），
臂与臂之间唯一的差别是开关，没有需要拍脑袋的权重。

> **稠密通道的向量已入库**：6400 块 × 1024 维（`BAAI/bge-m3@1024`），
> 走硅基流动 `/v1/embeddings`，发送内容仅为块的源码正文（不含路径与元数据）。

### 对照实验（M5）

`uv run ci eval --project tapestry -n 25`，一道命令跑完 6 个臂 × 3 种题型，
写 `eval/reports/<run_id>/`。完整报告：[`eval/reports/run-f97b4c0d1f33-s7/report.md`](../eval/reports/run-f97b4c0d1f33-s7/report.md)。

样本：name 25 题、docstring 25 题、concept 12 题（该项目只有 12 个概念在源码里有实例）。
k=8，seed=7，括号内是 95% bootstrap 区间。

| 臂 | 命中@8 | MRR | Top-1 |
|---|---|---|---|
| `none`（不检索） | 0% | 0.000 | 0% |
| `bm25` | 81% [69, 90] | 0.691 [0.581, 0.793] | 63% |
| `hybrid`（+dense） | 89% [81, 95] | 0.729 [0.632, 0.819] | 63% |
| `symbol` | 42% [29, 55] | 0.288 [0.193, 0.392] | 19% |
| `concept` | 18% [8, 27] | 0.177 [0.081, 0.274] | 18% |
| **`full`（产品配置）** | **98% [95, 100]** | **0.823 [0.744, 0.895]** | **73%** |

分题型看，每个通道都只在自己的题型上强——这正是把通道做成开关的理由：

| 题型 | 最强单通道 | 产品配置 |
|---|---|---|
| `name`（知道名字） | `full` 0.893 / `hybrid` 0.790 | — |
| `docstring`（知道描述） | `bm25` 0.980（`full` 0.870，反而被稀释） | 命中仍 100% |
| `concept`（用了哪个概念） | **`concept` 0.917** vs `bm25` 0.042 | `full` 0.579 |

三条读法（都写进了报告的 caveats）：

1. **符号 / 概念通道不是「更好的 BM25」**，它们解决的是另外的题型。
   `symbol` 在 docstring 题上 0.013，`bm25` 在 concept 题上 0.042——
   拿单一题型评判「某个通道有没有用」会得出相反的结论。
2. **RRF 等权融合会稀释强通道**：concept 题上 `concept` 单独 0.917，
   四路全开掉到 0.579。命中率没掉（92%），掉的是名次。
   要修只能引入查询类型路由或加权，那是**又一个需要验证的设计**，
   不该在评测当天顺手加。
3. `n` 只有 12–25，区间很宽；臂间差值小于区间重叠时不下结论。

这一轮评测还揪出两个真 bug（都已修，见提交历史）：

- FTS 检索被 SQLite 重排成「对 6400 行逐行探 FTS」，单次 2–5 秒；
  加 `CROSS JOIN` 强制 FTS 先出候选集后约 5 毫秒（`test_bm25.py` 有查询计划断言）。
- 概念通道算完匹配强度就丢掉，导致强匹配概念的实例被弱匹配概念挤掉；
  改成 `匹配强度 × 实例置信度` 后，concept 题从 33% 升到 92%。

> 换本地模型只需改 `CI_EMBEDDING_BASE_URL`。

### 持续认知（M6）

增量索引把「重新跑一遍」变成「只算变了的」——**没变的行一行都不动**，
否则每个块看起来都是新的，「哪些知识过期了」永远没有答案。

- **真实验证**（织忆 40 个 commit：`agent-v1~40` → `agent-v1`）：
  1036 个符号变化；增量 20.7s / 全量约 30s。
- **等价性断言**（测试里逐项比对）：增量结果与全量重建在
  符号 / 块 / 边 / 模块 / 设计说明上完全一致。
- **变更说明**：`GET /projects/{id}/changes`、`ci changes`、Agent 的 `get_changes` 工具。
- **影响范围**：反向可达（call / references / inherits / decorator，默认 3 跳）。
  删除符号时**在删除前**快照调用者——入边会随 CASCADE 一起消失。
- **设计说明过期**：见 [ADR 0016](decisions/0016-design-staleness-by-evidence-loss.md)。
  第一版按 claim 查不到判定，在织忆上报了 5 条，逐条核对**全是误报**
  （事件名 `assistant.tool_calls`、前端组件 `ChatWindow`、环境变量名被当成了符号）；
  改成「上次有证据、这次没有」后，40 个 commit 的区间上报出 4 条，
  例如「UI 统一设计系统」引用的 archive 文档已经不在仓库里。
- 本地 `.ci` 里保留了测试项目 `tapestry-inc`，可直接
  `uv run ci changes --project tapestry-inc` 看真实输出。

> 增量索引的已知边界：只重解析**变了的文件**。如果某文件的 import 目标
> 被改坏，而该文件本身没变，它指向旧目标的边会随 CASCADE 消失，
> 不会自动重解析。这是「宁可少一条边，不要留一条假边」的取舍。

### MCP Server（M7）

`uv run ci mcp --project tapestry` 起一个 stdio MCP server，把 **15 个工具**
（14 个项目/知识工具 + `list_projects`）交给外部 agent。接入方式与工具清单见
[`docs/mcp.md`](mcp.md)。

真机验证（官方 `mcp` Python 客户端的 `ClientSession`）：

```
initialize            → codeinsight 0.1.0
list_tools            → 15 个工具
call_tool search_code → 文本 + structured_content.citations（3 条）
call_tool list_projects → 两个已索引项目 + 绑定标记
```

两个设计点：

- 工具表直接从 `ToolRegistry` 翻成 MCP schema，不重写第二份——
  两处各写一遍参数说明，迟早不一致。
- 教材工具的 `structured_content` 里**没有** `citations`：
  换了个入口，「教材不是项目证据」这条规则也不能松。

### 关系图与时间线（M8）

**关系图**：`GET /projects/{id}/graph` 对 `edge` 表做 BFS，返回节点、边与
`truncated`。真实数据上 `prepare_chat_stream` 一跳 = 23 节点 / 22 边，接口 0.27 秒；
`max_nodes` 默认 80，截断时前端必须显示提示——图看起来完整而实际缺一半，比画错更糟。

三个刻意的取舍：

- **只画能落到具体符号的边**（`dst_symbol_id` 非空）。动态调用解析不到目标就不画，
  图上没有悬空节点；能解析但 `confidence < 1` 的边画成虚线
  （[ADR 0017](decisions/0017-graph-projection-and-layout.md)）。
- **布局不用力导向**：跳数用分列表达；同一跳超过 6 个节点折到子列（否则 22 个
  邻居竖成一列，fitView 会把字缩到看不清）。纯函数可直接单测。
- **节点挂概念标签**：源文档 §2.2 的例子是「登录接口 → 身份验证 / 数据库 / Token」，
  那三个词是概念，不是符号。点标签直接打开概念卡（§2.6 双向）。

**时间线**：`GET /projects/{id}/timeline` 把 `index_run` / `change_record` /
`staleness_report` 拼成一条轴，**只读库、不重算**
（[ADR 0018](decisions/0018-timeline-read-only.md)）。全量索引没有逐状态文件数时
字段为 `null`，界面显示「N 个文件」而不是假装 `+0 ~0 −0`；明细复用
`/changes?since=<commit>`，列表不做 N 次请求。

**顺手修掉的离线缺陷**：Monaco 默认从 jsDelivr 拉 loader，内网/离线环境下
会永远停在「编辑器加载中…」。改为走 npm 包内的 Monaco（懒加载 chunk），
现在断网也能看源码。

## 里程碑与 ADR 的关系

每个阶段的**技术决策**都写进 `docs/decisions/`（ADR），**功能范围**写在本文。
两者分开：范围会随进度调整，决策会留下"为什么当时这么选、什么条件下该重评"。

见 [`decisions/README.md`](decisions/README.md)。

### 依赖关系（谁在等谁）

```
第1周  A: M1索引    B: 写概念本体      C: 前端骨架+mock
                    ↑ 零依赖            ↑ 零依赖
第2周  A: M2/M3     B: detector实现     C: 三栏工作台
                    ↑ 需要 A 的符号/边   ↑ 需要 A 的 API 契约(第1周已给)
第3周  A: M5评测    B: concept臂        C: 概念卡UI
                    ↑ 需要 B 的 detector ↑ 需要 B 的概念 API
```

**关键：A 线在第 1 周必须交付三份契约**（`docs/api-contract.md`、
`frontend/src/api/types.ts`、`fixtures/sample-index.json`），
否则 B/C 第二周就会空转。
