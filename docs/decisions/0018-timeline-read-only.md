# 0018. 时间线只读索引当时写下的数字，不重算

- **状态**：已接受
- **日期**：2026-10-24
- **影响范围**：`api/structure.py`（`/projects/{id}/timeline`）、
  `frontend/src/components/timeline/`
- **源文档**：§2.4「持续项目认知与架构演进」、§2.5「开发过程理解与变更解释」

## 背景

「项目认知会演进」这件事要能被看见：每次索引发生了什么、改了多少文件、
影响哪些模块、哪条设计说明失去了证据。

这些数字在 `index_run`（索引统计）、`change_record`（变更明细）、
`staleness_report`（过期判定）里已经各存一份。时间线有两种做法：

1. 读的时候**重新算**：拿 commit 区间再 diff 一次、重新判定过期；
2. **只读**当时写下的值。

## 决策

时间线只读库，不重算：

- 每一格是 `index_run` 或没有对应索引 run 的 `change_record`（例如 MCP 侧
  外部 agent 记账）。
- 数字不清楚时给 `null`，不给 0：全量索引不知道逐状态文件数，
  前端显示「688 个文件」，不显示 `+0 ~0 −0`。
- 展开明细才请求 `/changes?since=<commit>`——列表不做 N 次请求，
  明细也复用已有的读路径。
- 排序按时间从新到旧；没有可靠时间戳时 `at: null`，前端显示「时间未知」。

## 理由

- **写侧和读侧各算一遍必然漂移**：增量索引的统计口径包含「快照调用者」
  「删除前读取证据」这些依赖时序的步骤，读侧重演很难得到同一组数。
  漂移过的「变更说明」比没有更糟——用户没法知道该信哪个。
- **时间线要回答的是「当时认知是什么」**，不是「现在重新看当时会是什么」。
  即使后来发现某个 commit 的解析有 bug，历史条目也应该保持当时的样子。
- **成本**：读一条 SQL 和读三条 SQL 的区别；重算则是 O(diff)。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 每次读时重新跑 git diff | 慢，且无法复现「当时」的过期判定（需要当时的证据状态） |
| 只展示 `change_record` | 会漏掉全量索引（没有 change_record），而全量重建也是认知的一步 |
| 直接展示 `git log` | git 历史不等于认知历史：索引可能停在旧 commit，也可能重复索引同一 commit |

## 后果

- **得到的**：时间线与 `/changes`、`staleness_report` 使用同一份事实；
  数字可追溯到具体表。
- **失去的**：早期版本（M6 之前）的 `index_run.started_at` 误写了
  `time.monotonic()`，这些行没有可用时间戳——`_iso()` 会返回 `null`，
  前端显示「时间未知」，而不是把 monotonic 秒数当日期。新的索引已改为墙钟 ISO。
- **将来要付的**：如果以后要展示 git commit message，需要额外落库
  （当前只有索引时的 `change_record.summary`）。重复索引同一个 commit
  会产生多条内容相同的条目——这是真实发生过的操作，不合并。

## 重评条件

- 用户开始需要「按模块/概念过滤时间线」（当前只按项目）；
- 索引统计字段不足以回答常见问题，需要在写侧补字段——补在写侧，
  仍然不在读侧重算；
- 时间线需要跨项目对比时，重新考虑数据模型。
