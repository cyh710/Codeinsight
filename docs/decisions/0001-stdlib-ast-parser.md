# 0001. 用标准库 `ast` 而非 Tree-sitter

- **状态**：已接受
- **日期**：2026-10-23
- **影响范围**：`src/codeinsight/cognitive/parsing/`
- **源文档**：§3.2 技术选型（AST 一栏）、§3.2 末句

## 背景

源文档 §3.2 推荐 **Tree-sitter** 做结构化代码解析，同时在末句限定：
「第一阶段优先支持 Python 项目，后续通过**可扩展的语言解析模块**增加其他语言。」

单人项目，第一阶段只支持 Python。选解析器时要考虑：能否编译、跨平台是否要额外工具链、
以及**将来换语言时上层要不要改**。

如果什么都不做（直接用 `ast` 而不抽象接口），将来加第二种语言时，
解析调用点会散落在索引器各处，改动面不可控。

## 决策

**第一阶段用 Python 标准库 `ast`**，但**所有解析调用都经过 `LanguageParser` Protocol**
（`cognitive/parsing/base.py`）。新增语言 = 新增一个实现类 + 在 registry 注册，上层不改。

## 理由

- 标准库 `ast` 零依赖、零编译。Tree-sitter 需要编译 C 扩展或绑定原生库，
  在 Windows + uv 环境里是明确的跨平台坑。
- `ast` 给的是**带行列号的语法树**，符号抽取（类/函数/方法/装饰器/调用点）完全够用。
- 源文档已经要求"可扩展的语言解析模块"——`LanguageParser` 就是那个模块的边界。
- 依赖越少，`uv.lock` 越简单，面试时"为什么不用 tree-sitter"有确定答案
  （"第一阶段只有 Python，标准库够用；接口留好了，加语言是加一个类"）。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| Tree-sitter | 需要编译依赖；第一阶段只有 Python，能力过剩 |
| 直接用 `ast` 不抽象接口 | 将来加语言要改上层代码，违反"可扩展的解析模块" |
| `libcst` | 保留注释与格式信息，但对符号抽取是过剩的依赖 |
| 只用正则 | 拿不到结构，调用关系与继承关系都做不了 |

## 后果

- **得到的**：零编译依赖、装完即用；接口边界清晰，加语言成本 = 一个实现类。
- **失去的**：不支持多语言（第一阶段无所谓）；拿不到注释、格式信息、类型推断——
  这些在当前范围内都不需要。
- **将来要付的**：如果将来真要支持第二语言，需要评估 Tree-sitter 与 `ast` 的能力差，
  可能要把 `ParsedSymbol` 的字段扩一点（比如 `decorator_names`）。

## 重评条件

- 当**第二语言**进入范围时，重评 Tree-sitter（那时它能一次覆盖多语言，是净收益）。
- 当需要**注释级信息**（如"这个符号的 docstring 在哪一行"、TODO 标注）时，重评。
