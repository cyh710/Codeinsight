# 0012. 工具失败降级为可解释的错误，不抛异常

- **状态**：已接受
- **日期**：2026-10-23
- **影响范围**：`agent/tool.py`（`ToolResult.error`）、`cognitive/parsing/base.py`
- **源文档**：§2.3-1 不局限于单个代码片段、§5-5 可追溯解释

## 背景

工具会失败：文件不存在、参数不对、SQLite 忙、检索无结果、上游模型超时。

如果工具 `run()` 抛异常，那么：
- 整个 Agent 回合崩掉，用户只看到一句 stack trace；
- 模型**没有机会看到错误**，也就没法换个策略（比如改用另一个工具、
  换个参数、或者干脆诚实地说"找不到"）；
- 一次偶发失败会毁掉整轮已经积累的证据。

更隐蔽的一种失败是**解析失败**：一个文件有语法错误，
如果 `parse()` 抛异常，整次索引就失败了——一个坏文件毁掉整个仓库的索引。

## 决策

**工具与解析器都不抛异常，失败以结构化的形式返回。**

```python
@dataclass(frozen=True)
class ToolResult:
    content: str
    data: dict[str, Any] = field(default_factory=dict)
    truncated: bool = False
    error: str | None = None
```

约定：
- 工具失败 → `ToolResult(error="...")`，`content` 里给模型一句**可读的中文说明**
  （说明发生了什么、可以怎么办），而不是 stack trace。
- 解析失败 → `ParsedFile` 产出空符号集，由索引器记为 `skipped`，
  **不让整次索引失败**。
- 模型请求失败 → 重试（指数退避）→ 熔断 → SSE 推 `error` 帧，
  **不静默**（静默会让用户以为系统在思考）。

## 理由

- **模型需要看到错误才能自我修正**。这是 Agent 与传统程序最本质的区别之一：
  一个好的工具错误消息应该让模型改掉下一次调用。
  这是 ReAct 范式的基本前提。
- **"找不到"是一个合法的答案**。§2.3-6 要求区分事实与推断，
  §4.3 的流程允许"按需继续深入或直接返回项目"——
  检索无命中时，**明确说没找到**是正确行为，不是错误。
  把它做成 `abstained` 而不是异常，语义才对（见 [0007](0007-facts-vs-inferences.md)）。
- **一个坏文件不能毁掉整个索引**。真实仓库里一定有语法错误、被截断的文件、
  生成到一半的代码。索引器必须能跳过它们并记录，而不是崩掉。
- 这是织忆验证过的模式（见 `docs/ported-from-tapestry.md`）：
  那边 MCP 返回 `isError=True` 时会补一句"工具报告失败，不要声称成功"——
  即**把错误转成模型能理解的信号**。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 抛异常，由 runtime 统一捕获 | 模型看不到错误内容，无法自我修正；且错误信息容易丢上下文 |
| 静默返回空结果 | 模型会以为"确实没有"，可能编造；且违反"不允许编造 `file:line`" |
| 抛异常并终止整轮 | 一次偶发失败毁掉整轮已积累的证据 |
| 让解析失败跳过整个文件但不记录 | 无法诊断"为什么这个仓库少了 3 个模块" |

## 后果

- **得到的**：模型能自我修正；单点失败不毁全局；失败可观测（`skipped` 列表）。
- **失去的**：每个工具都要自己处理错误分支，写起来啰嗦；
  忘记处理某个异常路径时，异常还是会漏出去——所以需要一条"工具不得抛异常"的测试断言。
- **将来要付的**：错误消息的措辞会影响模型行为，需要在评测里观察并调优。

## 重评条件

- 当**写工具**（`mutating=True`）被加回来时，本决策要重新审视：
  写操作失败可能需要**回滚**，不能只降级。
  那时参考织忆的 action digest 三段式（create → claim → finish）。
