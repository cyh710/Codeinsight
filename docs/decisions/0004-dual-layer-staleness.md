# 0004. 过期判定用符号级 + 文件级双层哈希

- **状态**：已接受
- **日期**：2026-10-23
- **影响范围**：`storage/schema.sql`（`chunk.source_sha256`、`chunk.file_content_sha256`、
  `file_snapshot`、`v_stale_candidate` 视图、`staleness_report`）
- **源文档**：§2.4 持续项目认知、§6「持续认知能力：代码变化后索引更新准确率、**过期信息比例**」

## 背景

源文档 §6 把「**过期信息比例**」列为持续认知能力的核心指标。
要测这个指标，数据层必须能回答："**当前索引里，有多少内容已经和仓库里的真实代码不一致了**"。

直觉做法是记一个文件级哈希：文件变了 → 里面的 chunk 都过期。
但这个做法**会误报**：一个 500 行的文件里改了一行注释，
另外 499 行对应的 chunk 根本没变，标成过期是错的。

反过来，只记符号级哈希则没法做秒级体检——每次体检都要重新解析所有文件。

## 决策

**记两层哈希，各管一件事：**

| 层 | 字段 | 用途 | 精度 |
|---|---|---|---|
| 符号级（精确） | `chunk.source_sha256` / `symbol.source_sha256` | **判定过期** | 精确 |
| 文件级（粗筛） | `chunk.file_content_sha256` + `file_snapshot` | **秒级体检** | 粗（会误报） |

配套：
- `file_snapshot(project_id, commit_sha, path, content_sha256)` —— 每个 commit 下每个路径的内容哈希。
- `v_stale_candidate` 视图 —— 文件级粗筛的现成查询。
- `staleness_report` 表 —— 每次 commit 记录 `total_chunks / stale_chunks / stale_rate / by_reason`。
- `index_run.stale_chunks` —— 索引时同步记录。

**指标定义**：

```
stale_rate = (# chunk 其 source_sha256 ≠ 当前 commit 下同符号的 source_sha256) / (# chunk)
```

分子**包含"符号已删"**。

## 理由

- **精确判定必须到符号级**。文件里改一行注释不该让整个文件的 chunk 变过期——
  否则 `stale_rate` 会被系统性高估，指标失去意义，也没法指导增量更新做到多细。
- **粗筛视图仍然需要**。它给出"哪些文件可能动了"的秒级视图，
  用来决定增量索引要重解析哪些文件——**用文件级做"要不要重解析"的判断，
  用符号级做"到底过没过期"的判断**，各司其职。
- **设计说明也会过期**（源文档 §2.4 第 5 问：「哪些历史设计说明已不再适用？」）。
  这条走 `design_decision.claims_json` 声称的机制与当前代码的比对，
  是与代码位置过期**并列**的第二类过期，不混在 `stale_rate` 里。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 只记文件级哈希 | 误报严重，`stale_rate` 高估，增量更新粒度被迫到文件级 |
| 只记符号级哈希 | 无法做秒级体检；每次判断都要重新解析 |
| 每次全量重解析后 diff | 慢，且放弃了"增量"这个核心命题 |
| 不做过期检测 | §6 明确要求这个指标；且持续认知无从谈起 |

## 后果

- **得到的**：`stale_rate` 可信；增量更新可以做到符号级；体检与判定各用合适的工具。
- **失去的**：每个 chunk 多存一个 64 字节哈希；
  增量更新时要做"新旧符号哈希对比"这一步（不比就不知道谁变了）。
- **将来要付的**：`file_snapshot` 会随 commit 数增长，需要保留策略
  （只留最近 N 个 commit 的快照）。

## 重评条件

- 当 `file_snapshot` 超过 **10 万行**时，加保留策略或改成只存增量。
- 当需要回答"这个 chunk 是在哪个 commit 变过期的"时，
  需要给 chunk 加 `last_changed_commit` 字段——那时重评表结构。
