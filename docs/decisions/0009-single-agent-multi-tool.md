# 0009. 单 Agent + 多工具，不做多 Agent 协作

- **状态**：已接受
- **日期**：2026-10-23
- **影响范围**：`agent/`（runtime、tools、context）
- **源文档**：§3.1 第二层「系统**优先采用单 Agent 与多工具相结合**的设计，降低复杂度」、
  §9 边界「自研单 Agent，不进行复杂多 Agent 协作」

## 背景

源文档两处明确限定单 Agent：§3.1 第二层的职责说明，以及 §9 边界。

但源文档 §2.3-3 提了一个容易与单 Agent 冲突的要求：
「**根据提问自动调整分析范围**」——问"这个接口的数据从哪来"，
Agent 要能自己去拉调用者、决定搜几个、要不要顺着 import 追下去。
这看起来像"多角色分工"。

## 决策

**一个 Agent，一组只读工具，工具调用循环由同一个运行时驱动。**

不引入：编排层、角色分工、子 Agent 派生、Agent 间通信协议。

"自动调整分析范围"由**工具**实现，而不是由多个 Agent 实现——
Agent 决定调哪个工具、传什么参数、要不要再调一次，这是同一个 Agent 的决策，
不需要拆成多个。

## 理由

- **源文档明确要求**，且给了理由："降低复杂度"。
- **多 Agent 的收益在这个项目里不成立**。多 Agent 的典型收益是"并行处理互相独立的子任务"
  或"用不同角色的视角交叉验证"。CodeInsight 的任务是**围绕一个问题组织证据**，
  本质是单线程的检索-推理过程，并行化收益低，而协调成本（上下文传递、
  结果合并、失败归因）是实打实的复杂度。
- **单 Agent 更好评测**。§6 的对照实验要能解释"是谁做了什么"——
  单 Agent 的每一步都是工具调用，可以逐条落进事件表。
  多 Agent 下"答案从哪来"会变得模糊，`citation_precision` 就难算了。
- **单人项目的失败模式**：多 Agent 系统最容易变成"看起来很复杂、实际上调试不动"。
  这是要避开的。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 多 Agent（规划者/检索者/解释者） | 协调成本 > 收益；调试困难；评测归因变糊 |
| Plan-and-Execute 两阶段 | "自动调整分析范围"要的是循环内的自适应，不是预先规划 |
| ReAct 之外的复杂范式 | 源文档 §3.1 明确"自研 Tool Calling Runtime" |
| 一个 Agent 但拆多个角色 prompt | 伪多 Agent，没有收益只有噪音 |

## 后果

- **得到的**：架构简单，行为可预测；每一步工具调用可追溯、可评测；
  与 §6 的对照实验设计直接兼容。
- **失去的**：无法做真正的并行检索；无法用"多视角交叉验证"来提高答案可靠性。
- **将来要付的**：单个 Agent 的工具集可能变大（M3 有 12 个工具），
  需要靠**清晰的工具描述**与**上下文装配**来避免选择困难。

## 重评条件

- 当单 Agent 的工具选择准确率明显下降（模型经常挑错工具）时，
  重评是否引入"检索专用子流程"——但仍然是单 Agent 内的子流程，不是多 Agent。
- 当评测显示**并行检索**能显著提升 Recall@K 时（例如需要同时扫多个大模块），
  可以让单个工具内部并行，而不是拆 Agent。
