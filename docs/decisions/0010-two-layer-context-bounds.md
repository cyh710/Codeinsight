# 0010. 上下文两层分别设界

- **状态**：已接受
- **日期**：2026-10-23
- **影响范围**：`config.py`（上限常量）、M3 的 `agent/context.py`
- **源文档**：§3.2 技术选型「上下文管理」、§3.1 第二层「项目上下文选择」

## 背景

源文档把「上下文管理」列为六项核心技术之一。
一个 Agent 的上下文有**两个来源完全不同的量**：

1. **持久化层**：工具结果**完整存进数据库/事件表**——这是账本，不能丢。
   如果这里也截断，就再也拿不回完整结果了。
2. **模型上下文层**：本轮发给模型的那部分——这个**必须有界**，
   否则几个大文件就能撑爆窗口。

如果不区分这两层，会出两类问题：
- 把持久化层也截了 → 账本不完整，无法回溯；
- 用同一个上限管两层 → 数值互相牵制，要么模型上下文太紧，
  要么账本里塞了永远用不到的全量内容。

## 决策

**两层各有独立的上限常量，互不引用。**

| 层 | 常量 | 初值 | 含义 |
|---|---|---|---|
| 持久化 | `max_tool_result_bytes` | 80,000 | 单个工具结果**入库**上限 |
| 模型 | `max_context_bytes` | 64,000 | 单轮序列化上下文**总**上限 |
| 模型 | `max_context_message_bytes` | 24,000 | 单条模型消息上限 |
| 模型 | `max_tool_calls_per_turn` | 16 | 每轮工具调用次数 |
| 模型 | `max_model_turns` | 10 | 每轮模型循环次数 |

加上织忆那边验证过的两个：单工具结果 12,000、单组工具调用 32,000。

**截断用同一个对象写记录与事件**——保证"账本里看到的"与"模型看到的"来自同一份数据，
不会出现"账本里有、模型没看到"或反之。

## 理由

- **源文档明确要求**。§2.3-1「不局限于单个代码片段」意味着上下文里要有邻域，
  而邻域会迅速膨胀——必须有界。
- **截断一致是正确性要求，不是优化**。如果两处截断规则不同，
  回答里引用的内容可能与账本里的内容对不上，评测的 `citation_precision` 就没有意义。
- **分层之后可以分别优化**。持久化层可以放宽（存储便宜），
  模型层必须收紧（每 token 都要花钱）。混在一起就只能取一个折中值，两边都不舒服。
- 这条经验直接来自织忆（见 `docs/ported-from-tapestry.md`）：
  那边的教训是"工具结果同时进记录和事件流，两处若截断不一致，
  就会出现'账本里有、模型没看到'或反之"。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 单一上限 | 两层诉求相反，混用必然两边都别扭 |
| 只按 token 数限制 | 代码片段的"有用程度"与 token 数不成正比；且实现更复杂 |
| 不限制，靠模型自己看 | 不可靠；一次读整个大文件就超窗 |
| 按"最近 N 条消息"限制 | 不控制单条消息的大小，一条巨长消息就能超 |

## 后果

- **得到的**：上下文可控且可预测；账本完整；两层可独立调参；评测可复现。
- **失去的**：模型可能因为截断看不到关键内容——需要靠检索质量与截断策略缓解。
- **将来要付的**：截断必须**优先保留结构化引用**（见 [0006](0006-citation-outside-content.md)），
  否则截断会毁掉引用。

## 重评条件

- 当评测显示**因截断导致的错误引用**占比 >5% 时，提高模型层上限或改截断策略
  （优先保留被引用的片段）。
- 当模型上下文上限（provider 侧）显著变大时，重新校准这两组常量——
  现在它们是照搬织忆的量级，不是从本项目的实际数据推出来的。
