# 0015. 索引范围分三档，检索层不引入打分系数

- **状态**：已接受
- **日期**：2026-10-24
- **影响范围**：`cognitive/indexing/scanner.py` · `cognitive/indexing/chunker.py` · `cognitive/retrieval/*`
- **源文档**：§2.1-1/2/3 · §2.4-5 · §2.5-6 · §2.6 · §5-2 · §5-4

## 背景

M1 要给真实仓库建索引。被测仓库是织忆 `ai-companion-agent@agent-v1`，实测 696 个文件：

| 目录 | 文件数 | 是什么 |
|---|---|---|
| `backend/` | 183 | 自己的后端代码（Python） |
| `frontend/` | 152 | 自己的前端（TS/JS） |
| `tests/` | 149 | 测试代码（Python） |
| `docs/` | 70 | 文档，**含 33 篇 ADR** |
| `scripts/` | 51 | 自己的脚本 |
| `skills/` | 34 | 自己的 skill 定义 |
| `mobile_sam/` | 16 | **第三方**图像分割模型 SAM 的代码 |
| `desktop_pet/` | 11 | 桌宠 |
| `build_cache/` | 1 | **二进制** BPE 词表（`tiktoken/9b5ad71b…`） |

389 个 `.py`。实测解析全量只要 **1.9 秒**（`ls-tree` 31 ms + `cat-file --batch` 310 ms +
`ast.parse` 1600 ms，产出 492 个类 + 4972 个函数）。

**真正要决策的不是"重不重"，而是"哪些文件参与检索"。**

## 决策

范围分**三档**，每档的规则是**客观的 0/1 分类，不是打分**：

### 第一档 · 不进索引（排除）

`build_cache/`、`node_modules/`、`.venv/`、`dist/`、`*.min.js`、所有二进制文件、`*.lock`。

理由：不是代码，或不是这个项目的代码。二进制无法解析，也无意义。

### 第二档 · 符号入库，chunk 不入库

`mobile_sam/`（第三方 SAM 代码）→ `role='vendored'`，`in_index=1`（符号进），
但**不生成 chunk**，因而不参与 BM25 / 向量 / 符号三路检索。

理由有两面，都要占：
- **留住证据**：项目 `import` 了 `mobile_sam.SamPredictor` → 这条 `imports` 边是
  "本项目用了 SAM 做图像分割"这条**设计事实**的载体。源文档 §2.6 说系统要能
  自动识别项目中的相关概念——如果第三方代码整体不索引，"用了 SAM"这个结论就查不到。
- **不污染检索**：第三方内部实现不该出现在"这个项目怎么做的"的答案里。

### 第三档 · 全量入库，同等对待

`tests/`、`docs/`、`scripts/`、`skills/`、`backend/` —— **符号和 chunk 都入库，
检索时不做任何降权**。

`docs/` 的 `.md` 由 A6 单独走设计说明索引（§2.4-5），不进 chunk 检索。
`frontend/` 保留在文件树，但语言不是 Python，不进符号索引（本项目 Python-only，
`LanguageParser` 留扩展口）。

## 理由

**核心依据是源文档 §5 的评测不能被人为偏置污染。**

ADR 0003 已经立过一条规矩：中文不做分词会系统性压低中文重的 chunk，
**让 BM25 臂的劣势变成假象，污染对照结论**。检索降权是**同一类错误**——
给测试文件乘 0.6，等于在对照组里偷偷塞了一个没有依据的假设，
"关掉降权"就变成了第二个未受控变量。

所以：**能在索引阶段用客观规则表达的，不留到检索阶段用系数表达。**
- "这是第三方代码" → 客观分类 → 不让它参与检索。
- "这是测试代码" → **不是**客观的"不是本项目的代码" → 参与检索，不打折。

**为什么 `tests/` 要全量同等对待（这是本决策最容易被质疑的一点）**：

1. **§2.5-6 明确要求"关联相关测试结果"**，§2.4-6 要求测试记录落库。
   测试不进索引 → 这两条功能没有素材。
2. **§2.6 概念检测的实例富矿在测试里**。本体里的
   `db-transaction`、`file-lock`、`retry-idempotency`、`abstract-base`、
   `dependency-injection` 在测试代码里的命中量远大于主代码——
   测试里的 fixture 注入就是依赖注入，测试里的 fake 类就是继承基类，
   测试里的重试 mock 就是幂等性实现。验收标准是"人工核对准确率 ≥ 0.8"，
   靠主代码单一来源很难稳定达标。
3. **撞名问题有专门的机制解决**。契约 §4.2 已经有 `ambiguous` + `alternatives`
   字段（织忆里 `main` 定义了 33 次、`FakeMemory` 8 次）。
   **用标记告诉用户"这个名字有 N 处定义"，比悄悄改分数更诚实**，
   也比删数据更不破坏。

**为什么 `mobile_sam/` 要符号入库而不是整体排除**：
排除更简单，但那样"项目用了 SAM"这条 import 边就断了。
`role='vendored'` + 不生成 chunk 是唯一能同时满足两头的做法：
符号图完整，检索干净。

**为什么"重要符号"用三项加权**（同批决定）：
源文档 §2.1-4 只说"提取重要类、函数、方法、符号"，没给定义。
单看被引用数 → `get`/`init` 这类高频小函数上榜首；
单看行数 → 自动生成的大函数上榜首。
`score = 0.5×归一化被引用数 + 0.3×归一化行数 + 0.2×命名启发`
三项加权能同时压住这两类噪声。权重写在代码常量里，可调。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 检索时给测试文件乘 0.6 降权 | 引入无依据的偏置，污染 §5 的对照实验（见上） |
| 完全排除 `tests/` | §2.5-6 / §2.4-6 没有素材；概念检测准确率难达标 |
| 完全排除 `mobile_sam/` | "项目用了 SAM"这条设计事实查不到，§2.6 受损 |
| `mobile_sam/` 也生成 chunk 参与检索 | 第三方实现污染答案，且要在答案里区分"这是项目代码" |
| 索引时手工维护"哪些文件重要"的名单 | 源文档 §5 说的"持续认知"要求索引能随代码自动更新，手工名单必然过期 |

## 后果

- **得到的**：检索结果只含项目自己的代码；零检索调参；概念检测实例充足；
  测试证据有素材；"第三方用了什么"可查。
- **失去的**：测试代码和主代码同名时，检索排序仍可能被测试里的实现顶上来
  （用 `ambiguous` 标记缓解，不消除）。
- **将来要付的**：三档规则写在 `scanner.py` 的常量表里，
  若被测仓库结构变化（比如换了 vendored 目录名）要改这一张表。

## 重评条件

出现以下任一情况时重新评估：

- §5 的评测显示"开/关概念关联"这一臂的差异**小于**噪声区间
  → 说明概念实例的来源分布有问题，要重看 `tests/` 的定位；
- 人工核对概念检测准确率**低于 0.8** 且排查后确认不是标注问题
  → 重新考虑是否要把 `tests/` 降权或部分排除；
- 引入第二个被测仓库（开源项目）后，vendored 目录命名规则明显不统一
  → 把第一档/第二档改成基于 `git submodule` + 依赖声明的自动判定，而不是路径名单。

当前触发条件：M5 评测出第一份带 CI 的报告时，用真实数据回看这一决策。
