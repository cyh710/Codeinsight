# 0005. 切块按符号边界，超大符号二次切分

- **状态**：已接受
- **日期**：2026-10-23
- **影响范围**：`cognitive/indexing/chunker.py`、`storage/schema.sql`（`chunk.ordinal` / `part_count`）
- **源文档**：§2.1-4 提取代码符号、§5-2 结构化检索

## 背景

代码检索的检索单元怎么切，决定了定位准确率的上限。

- **固定字符窗口**（RAG 里的常规做法，如 512 字符一块）会把函数拦腰截断，
  检索命中的是"半个函数"，回答时给出的 `file:line` 指向一个不完整的上下文。
- **纯符号边界**听起来完美，但符号大小差异极大。

实测（候选被测仓库：Tapestry `agent-v1`）：
`backend/services/chat_orchestrator.py` 单文件 **2229 行 / 97 KB**，
其中 `prepare_chat_stream` 单个函数接近一千行；`ilink_bot.py` 96 KB、`pet_image_pack.py` 86 KB。

一个 1000 行的函数切成一个 chunk，会：
1. 稀释向量语义（embedding 一大段代码，语义被摊平）；
2. 被 BM25 的长度归一化压死（长文档得分天然低）；
3. 在模型上下文里占掉大量预算却只对应一个符号。

## 决策

**切块以符号为原子；超过 `MAX_CHUNK_LINES`（默认 120 行）的符号，按语句/块边界二次切分。**

```sql
ordinal     INTEGER NOT NULL DEFAULT 0,   -- 超大符号二次切分时 >0
part_count  INTEGER NOT NULL DEFAULT 1,
symbol_id   INTEGER NOT NULL REFERENCES symbol(id) ON DELETE CASCADE,
```

关键约束：**二次切分后的 chunk，`symbol_id` 仍指向原符号**，
`qualname` 也保留原符号的。于是：

- "这个符号在哪" 依然只有一个答案（不会因为切分出现多个"定义位置"）；
- 检索命中的是符号的一部分，但仍然能定位到正确的符号与行号区间；
- 需要完整符号时，可以按 `symbol_id` 把多块拼回去。

## 理由

- **符号是代码的天然语义单元**。用户问"X 在哪实现"，期望的答案边界就是符号边界。
  固定窗口切出的"半个函数"既不满足检索，也不满足展示。
- **超大符号必须切**，否则单个 chunk 会主导向量与 BM25 的行为。
  切的时候保持 `symbol_id` 不变，就把"检索粒度"和"符号语义"这两件事解耦了——
  检索可以细，语义仍然指向符号。
- 120 行这个初值来自上面那些实测文件：一个 1000 行函数切完约 8 块，
  每块仍是完整的一段逻辑，语义不散。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 固定字符窗口 | 截断函数，定位不准，展示残缺 |
| 只按文件切 | 一个文件可能几千行，检索单元太大 |
| 只按类切 | 类也可能有几千行（`ChatOrchestrator`），且函数级的定位精度不够 |
| 纯符号边界不二次切分 | 巨型 chunk 稀释语义、被 BM25 压死 |
| 树形切块（AST 子节点递归） | 更精细，但实现与调试成本高；先做行数阈值，够用再升级 |

## 后果

- **得到的**：定位精确到符号；超大符号不支配检索；`symbol_id` 保持唯一语义锚点。
- **失去的**：chunk 与符号不再一一对应，代码里要有"由 chunk 反查完整符号"的逻辑。
- **将来要付的**：二次切分的边界选择（按语句还是按块）要保证不切开一个逻辑单元；
  这是需要单元测试的地方。

## 重评条件

- 当评测显示**超大符号的召回明显偏低**时，改为 AST 子节点递归切块。
- 当 `MAX_CHUNK_LINES` 需要按语言分别设定时（第二语言进来时），把它挪进
  `LanguageParser` 的返回值而不是全局配置。
