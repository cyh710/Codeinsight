# 0016. 设计说明过期用「证据消失」判定，而不是「claim 查不到」

- **状态**：已接受
- **日期**：2026-10-24
- **影响范围**：`cognitive/changes/staleness.py`、`cognitive/changes/incremental.py`、
  `cognitive/changes/service.py`
- **源文档**：§2.4 第 5 问「哪些历史设计说明已不再适用」

## 背景

§2.4 的第 5 问是全项目最硬的一条：「代码会过期，设计说明也会过期」。
M1 的 `design_docs.py` 已经从 ADR 里抽出结构化 claim：

- `kind=path`：文档提到 `archive/docs/UI_REVIEW.md` → 声称这个文件存在；
- `kind=symbol`：文档提到 `` `chunk_bm25` `` → 声称有这个符号。

最初的判定很直接：**当前索引里查不到这条 claim，就说明设计说明过期了。**
所有 claim 都查不到 → 报过期。

## 决策

改成**前后对比**：

> 上一次索引时这条设计说明还能在代码里定位到证据（`design_decision_evidence`
> 非空），这一次一条都定位不到了 → 判过期。

判定在增量索引时算一次，写进 `staleness_report.by_reason`；
读路径（`GET /changes`）直接取报告，不重算。

## 理由

在织忆上实测，按 claim 判定的第一版报了 5 条过期，逐条核对**全是误报**：

| 文档 | 被当成 symbol 的 claim | 实际是什么 |
|---|---|---|
| 0039 上下文边界 | `assistant.tool_calls` / `tool.finished` | **事件名**（字符串常量），本来就不是符号 |
| 0019 分支选择 | `opening` / `ChatWindow` | 前端组件 / JSON 字段，不在 Python 符号表里 |
| 0026 持久运行时 | `WX_BOT_ENABLED` / `getupdates` | 环境变量名 / 微信 API 方法名 |

反引号里的东西不全是符号。用「查不到」当过期信号，等于把「ADR 提到了一个
不是符号的词」判成「这个设计已经不适用了」——而用户只有亲手去翻代码
才能发现是误报。误报一次，这个提示就废了。

「证据消失」没有这个问题：它要求**同一份文档**在两次索引之间**从有证据
变成没证据**。没证据过的文档永远不报；文档被删了不报（那是文档问题，
不是代码问题）。

## 代价

- 只能发现「上次有、这次没有」的情况，**新加入的过期判定拿不到**
  （比如第一次索引时就已经过期的 ADR）。这是有意的：宁可漏报。
- 需要 `design_decision_evidence` 在改动**之前**读取——删符号会 CASCADE
  掉证据行，晚一步读到的永远是 0。`incremental.py` 里这行必须排在
  所有删除之前（有注释钉住）。
- 全量重建会清空证据再重写，等于「没有前后对比」——所以全量索引不产出
  过期报告，`GET /changes` 在只有全量索引的项目上返回空列表。

## 备选方案

1. **claim + 代码文本匹配**：符号名在任意 chunk 的 body 里出现就算它还活着。
   否决：删掉函数后，过期 import 还留着它的名字，文本里仍然能搜到——
   那正是最该报过期的时刻。
2. **LLM 判断文档与代码是否一致**：否决。评测口径要求确定性、可复现，
   而且成本高到没法每次索引都跑。
3. **保留证据历史表**（每次索引存一份证据快照）：更通用，但多一张表、
   多一份会无限增长的存储。当前只需要「上一版」，读一次就够。
