# 0011. 概念本体是人工策展的 YAML，不是自动生成的知识图谱

- **状态**：已接受
- **日期**：2026-10-23
- **影响范围**：`knowledge/concepts/*.yaml`、`cognitive/concepts/`（ontology / detector / explain）
- **源文档**：§2.6 项目关联知识探索、§9 边界「**不追求建立包含所有编程知识的通用知识图谱**」

## 背景

源文档 §2.6 要求系统能识别项目中的技术概念（JWT、Redis 缓存、依赖注入、
异步编程、数据库事务、设计模式、算法与数据结构），并支持三级深度与双向导航。

有一个诱惑是：**让 LLM 自动从代码里"发现"概念并写出解释**——
看起来全自动，维护成本为零。

但如果这么做：
- 同一个概念每次生成的名字/边界都不一样，无法稳定地做双向导航；
- "设计权衡"这种内容，模型每次会写出不同的话，评测无从谈起；
- 无法回答"这个仓库一共涉及哪些概念"——每次结果都不一样。

## 决策

**概念本体是人工策展的静态资产，放在 `knowledge/concepts/<id>.yaml`，一个概念一个文件。**

```yaml
id: jwt
name: JWT 身份认证
category: auth
summary: 用签名令牌承载身份声明的无状态认证机制。
principles: |
  载荷编码后用对称/非对称密钥签名，验证方只需验签不需查库。
tradeoffs: |
  换取无状态与可水平扩展，代价是签发前无法即时吊销。
alternatives: |
  会话 ID + 服务端存储；不透明令牌 + 撤销表。
detection:
  import_names: [jwt, jose, pyjwt, authlib]
  call_names: [jwt.decode, jwt.encode]
  attribute_names: [Authorization]
  decorator_names: [requires_auth, verify_token]
```

**"概念 → 代码位置"不手工维护**，而是由 `detection` 声明式规则
在符号 / 导入 / 调用 / 装饰器边上**自动派生**出 `concept_instance`。
代码改了，重跑检测即同步——这张表永远不会过期。

三级深度对应不同成本：

| 深度 | 来源 | 是否调 LLM |
|---|---|---|
| 快速理解 | 本体 `summary` 直读 | **不调** |
| 结合项目 | 自动派生的实例 + 调用图 | 轻量串场 |
| 深入探索 | 本体 + 本项目实例 | 重 |

## 理由

- **源文档的边界正好支持这个规模**：§9 说「不追求建立包含所有编程知识的
  **通用知识图谱**」。也就是说，源文档本身就认为第一版应该是**有限、有边界**的，
  而不是全量自动生成。
- **"设计权衡"必须是写下来的**。它是这个概念最值钱的部分，也是最不能靠
  通用定义生成的部分——"JWT 换取无状态，代价是不能即时吊销"这句话，
  要由人写，且写一次就固定下来。
- **自动派生保证了"这张表不会过期"**——这正是我最初误判的地方。
  人工要维护的是**概念本身**（定义、原理、权衡、检测规则），
  不是**概念在代码里的位置**。
- **可增量、可评审、可贡献**。一个 YAML 一个概念，PR 友好；
  对照 [§9 的"不追求通用知识图谱"](https://example.com)，20–40 个概念起步完全够。
- **三级深度里前两级不调 LLM**，既是零延迟零成本，也**可写断言测试**——
  只有第三层需要评测。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| LLM 自动发现并解释概念 | 每次结果不一致；双向导航无法建立；评测无从谈起 |
| 从 Wikipedia / 课程抓取概念定义 | 版权与出处问题；且"设计权衡"讲的是通用原理，不讲本项目的取舍 |
| 只做代码 → 知识，不做知识 → 代码 | 源文档 §2.6 明确要双向导航 |
| 用 LLM 起草 + 人工审 | 可行但**当前不默认**：先把 20 个手工精写出来，跑通评测，
再评估是否值得引入起草流程（会引入"起草稿与终稿不一致"的版本管理问题） |
| 做一个完整的概念本体编辑器 | 单人项目，YAML + PR 足够 |

## 后果

- **得到的**：概念稳定可引用；双向导航成立；三级深度有确定的可测部分；
  本体本身是可评审、可贡献的资产。
- **失去的**：起步要写 20–40 个概念，**约 15–25 小时**。这是实打实的成本。
- **将来要付的**：概念覆盖不到的技术，用户会觉得"这个它不懂"；
  需要一个"未识别"提示，而不是假装没有这个概念。

## 重评条件

- 当评测显示**概念检测的精确率 <0.7** 时，说明检测规则太宽，要收紧而不是加概念。
- 当用户频繁需要"它不认识的概念"时，评估"LLM 起草 + 人工审"的流程。
- 当本体超过 **100 个概念**时，需要考虑按类别拆分目录与检索策略。
