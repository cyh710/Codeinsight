# 0014. 文件分类用单列 `role`，不用三个布尔列

- **状态**：已接受
- **日期**：2026-10-24
- **影响范围**：`storage/schema.sql` 的 `file` 表 · `cognitive/indexing/scanner.py` · API 的 `GET /projects/{id}/files`
- **源文档**：§2.1-1（识别依赖和配置）· §2.1-2（解析文件目录）· §3.1 第一层「交互展示层」

## 背景

M1 要给仓库里的每个文件打分类标签，供两处消费：

1. **索引器**决定哪些文件进符号索引（第三方代码不进）。
2. **前端文件树**决定怎么显示（第三方代码折叠、测试文件弱化、配置文件单独分组）。

原 schema 里是三个布尔列 `is_generated` / `is_vendored` / `is_test`。

**如果什么都不做**：三个布尔列能表达"是测试文件"和"是第三方代码"，但表达不了
"**这个文件算什么**"——前端拿到的是三个 bit，得自己决定优先级；
"既是 vendored 又是 test"这种组合没有意义却是合法的，会让每个消费者都得写一遍优先级逻辑，
三处消费者写三遍就可能写出三种结果。

源文档 §2.1 的表述是"解析文件目录与项目入口"、§3.1 要求前端能按项目结构组织视图，
都指向**一个分类**而不是一组标记。

## 决策

`file` 表用一个互斥的 `role` 列取代三个布尔列：

```
role ∈ source | test | vendored | generated | config | doc
```

**优先级**（判定顺序，不可交换）：
`vendored > generated > test > config > doc > source`

- 第三方目录（`mobile_sam/`、`build_cache/`、`node_modules/`）→ `vendored`，且 `in_index = 0`
- 生成的代码 → `generated`
- `tests/`、`test_*.py`、`*_test.py` → `test`
- `pyproject.toml`、`*.yaml`、`*.toml` → `config`
- `*.md` → `doc`
- 其余 → `source`

保留 `in_index`（布尔）作为**独立**的一维：它说的是"进没进索引"，
和"这个文件是什么类别"是正交的两件事。

## 理由

- **前端的消费方式决定了数据结构。** 契约 §3.6 的 `FileRole` 就是单值 union
  （`source|test|vendored|generated|config|doc`）——如果库里是三个布尔，
  就要在 API 层再做一次"三个 bit → 一个 union"的映射，而映射的优先级规则必须和索引器一致，
  也就意味着**同一个优先级规则写两遍**。现在只有一处：索引器写 `role`，API 直接读。
- **布尔列允许无意义状态。** `is_vendored=1 AND is_test=1` 在数据上合法，
  但语义上"第三方代码里的测试"对用户没有价值。互斥的 `role` 让这种状态**写不出来**。
- **`in_index` 不能并进 `role`。** 文档、配置文件都不进符号索引，
  但它们有独立价值（架构概览要列出入口、文档要做设计说明索引），
  所以"进不进索引"必须能独立于"是什么类别"表达。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 保留三个布尔列，API 层做映射 | 优先级规则写两遍，容易漂移；无意义组合可写入 |
| 单列 `role` 但允许组合（用 `+` 拼接） | 前端要解析字符串；"test+vendored"这种组合仍然无意义 |
| 用 JSON 列存标记数组 | 查询要 JSON 提取，前端类型退化，收益为零 |
| 完全不分类，全量索引 | 检索会被第三方代码和测试代码带偏，污染 §5 的对照实验结论 |

## 后果

- **得到的**：单一事实来源；前端的分类判断是一行 `role === 'vendored'`；
  数据里不会出现无意义状态；契约的 `FileRole` union 与库结构天然一致。
- **失去的**：想同时表达"既是测试又是配置"要自己开新列（当前场景用不上）。
- **将来要付的**：新增类别时要同步改三处——`role` 的取值域、`api-contract.md` §1 的枚举、
  `types.ts` 的 `FILE_ROLES`。三处都是契约文件，由 A 线统一改，不难。

## 重评条件

出现以下任一情况时重新评估：

- 需要表达**正交**的多重标记（例如"既是生成代码又是测试"真的有分析价值）；
- 前端要按"多标签"过滤文件树（例如同时筛 `test` 和 `config`）。

当前触发条件：前端工作台（M4）上线后，如果文件树需要多标签筛选，
把 `role` 拆回布尔列并**保留** `role` 作为派生视图。
