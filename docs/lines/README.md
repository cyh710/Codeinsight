## 交接流程

| 情形 | 怎么办 |
|---|---|
| 需要改别人目录的东西 | 写 `docs/requests/NNNN-xxx.md`（模板见 [`../requests/README.md`](../requests/README.md)），**不要直接改** |
| 需要别人的数据 | 提需求要 **fixture 或接口**，不要直接读对方的库 |
| 发现设计与源文档冲突 | **以源文档为准**；确实要改，先写 ADR |
| 源文档没覆盖的空白 | 写 ADR 记录决策，再写代码 |
| 三个方向都不确定 | 停下来问用户，不要各自发挥 |

## 每个 agent 都要跟用户对齐

> 三条线同时跑，用户不在现场，所以**每个 agent 必须主动把决策点摆出来**，
> 而不是默默按自己的理解往下写。

| 线 | 开工前要问的 |
|---|---|
| A 线 | vendored 排除范围 · "重要符号"定义 · `tests/` 索引与否 · 评测仓库 · 五臂取舍 · 对外承诺 |
| B 线 | 20 个概念选哪 20 个 · 文案详细程度 · `tradeoffs` 要不要模板 · 检测规则宽严 · `string_markers` 要不要 |
| C 线 | 三栏各放什么 · Monaco 要不要 · 概念卡右栏还是弹层 · 暗色模式 · 界面语言 · 项目切换器位置 |

**提问格式**（别开放式甩问题）：

```
要做什么 · 2~3 个选项 · 我的推荐 + 理由 · 各自的代价
```

**必须问的**：需求边界 / 取舍 / 观感 / 范围变更 / 对外承诺。
**不用问的**：实现细节 / 规格已写死的 / 有唯一答案的技术问题 / 风格格式。

**问不到用户时**：查规格 → 查默认值 → 按默认值做 → 写 ADR 标注"未与用户确认" →
提交信息写 `决策：X（未对齐，默认值，理由：…）`。

完整规则见 [`../workspace.md` §9](../workspace.md)。

## 收工检查（每条线都要过）

```bash
uv run pytest -q        # A/B 线
uv run ruff check .     # A/B 线
cd frontend && npm run test && npm run lint   # C 线
```

- **绿了才提交。**
- 提交信息用中文，格式 `类型: 做了什么`，正文写动机与影响。
- `git commit` 可以直接做；**`git push` 必须等用户明确说。**
