# 八组讲解样稿

由本轮实现 agent 预写的候选表达，供人工风格评审；不是生产 Provider 实测效果或用户已经掌握的记录。
除第五组明确引用当前源码外，其余代码和数据都是教学例子，不表示导入项目采用它们。
标题、问题、说明是评审文档的组织方式，不要求实际回答复制这些栏目。
运行时只在相关且预算足够时选一个短例；完整样稿不整篇送入上下文。

## 1. SQL 是什么（sql）

用户：SQL 是什么？

SQL 是你向数据库表达“我要哪些数据、我要怎样修改数据”的语言。
数据库负责管理数据，表是其中一种组织数据的方式。先把一张表想成列名固定的表格：

| name | price |
| --- | --- |
| 笔记本 | 12 |
| 钢笔 | 35 |

假设这张表叫 products，你想找出价格不到 20 元的商品，可以写：

```sql
SELECT name FROM products WHERE price < 20;
```

这里 SELECT name 表示取出商品名，FROM products 表示从这张表里找，
WHERE price < 20 表示只保留价格低于 20 的记录。结果是“笔记本”。
你写的是需要的结果；数据库决定怎样把符合条件的数据找出来。

评审点：用同一张表串起术语与查询，没有先介绍全部 SQL 分类、数据库历史和复杂优化。

## 2. 函数参数（parameters）

用户：函数参数是什么？

参数是你调用函数时交给它的值。例如，这个函数负责拼出一句问候：

```python
def greet(name):
    return "你好，" + name

message = greet("小林")
```

定义函数时，name 是留给这次输入的位置。调用 greet("小林")，这一次 name 的值就是“小林”，
返回的字符串是“你好，小林”，随后赋给 message。
如果下一次调用 greet("小陈")，同一段函数就会返回“你好，小陈”。

name 这个位置通常叫形参，调用时传进去的“小林”叫实参。
先分清“函数留的位置”和“这次给的值”，再记这两个名字就容易些。

评审点：从调用中解释定义，具体值、返回值、变量明确对应，没有提前展开所有参数语法。

## 3. 列表共享（shared-list）

用户：为什么 b.append(3) 后 a 也变了？

看这三行：

```python
a = [1, 2]
b = a
b.append(3)
```

b = a 没有复制列表，而是让 b 也指向 a 正在指向的那个列表：

```text
a ─┐
   ├──→ [1, 2]
b ─┘
```

append 改变的是右边这个列表，它变成 [1, 2, 3]。a 和 b 仍然指向它，
所以从两个名字都能看到变化。
如果你需要两份可以分别增删元素的列表，可以用 b = a.copy()；
这个复制不会递归复制列表内部可能包含的其他可变对象。

评审点：先画出具体对象与名字；复制的边界只在给出替代写法时说明。

## 4. 按钮变了，数据没保存（request）

用户：页面都显示成功了，刷新怎么就没了？

页面显示成功和数据存下来，是两件事。
假设留言板的按钮点击后只执行了“变绿”，浏览器里就能出现成功的样子；
但如果留言没有发给服务器，下次刷新重新读取列表，列表里仍没有它。

可以沿着同一条留言核对：

| 位置 | 要确认的事情 |
| --- | --- |
| 浏览器 | 有没有发出包含这条留言的请求 |
| 服务器 | 有没有收到请求，处理是否成功 |
| 保存位置 | 有没有真正写入预期的数据 |
| 刷新读取 | 有没有从相同位置读回这条留言 |

只有按钮变色这一个现象，还不能确定是哪一步出了问题。
结合项目时应检查相关处理函数和请求结果，再确定原因。

评审点：把外观与状态分开，形成可验证的来路；不凭现象直接宣称数据库未提交。

## 5. 为什么还在解释旧代码（snapshot）

用户：我刚改完这个 Git 项目的代码，为什么索引里还是旧的？

保存文件会更新你正在编辑的内容，但已有索引可能仍对应之前的提交。
对 Git 仓库，CodeInsight **构建索引**时按指定提交读取文件树和文件内容。
实现可对照当前源码的 `_git_ls_tree` 和 `read_blobs`：
[扫描器](../../src/codeinsight/cognitive/indexing/scanner.py)。

假设同一个文件有两个版本：

| 位置 | 内容 |
| --- | --- |
| 索引对应的提交 | return "你好" |
| 当前刚保存的文件 | return "欢迎" |

如果索引读取的是前一份版本，它看到的仍然是“你好”。
所以需要分别确认“改动有没有进入目标提交”和“索引有没有更新到那个提交”。
固定版本便于查看历史关系，但正在编辑的内容可能还没进入这份索引。
普通新问题仍可直接阅读当前文件，不必等索引更新；当前阅读入口可对照
[工作区服务](../../src/codeinsight/cognitive/workspace.py)。
若点的是旧回答的来源，则会打开当时保存的版本，可主动选择“查看当前文件”。

评审点：区分索引构建、当前阅读和历史来源；不把“先提交再索引”当作阅读新代码的前提。

## 6. 依赖注入（dependency-injection）

用户：依赖注入到底解决什么问题？

假设保存订单需要一个数据库连接。函数可以自己创建连接，也可以接收调用者准备好的连接：

```python
def save_order(db, order):
    db.save(order)
```

这里 save_order 只管用 db 保存订单，创建和配置 db 的工作在调用它之前完成。
测试时，也可以传入一个只记录调用、不会真的写数据库的替身。
“把函数要用的东西从外面交给它”就是这里的核心想法。

这样做需要在调用处组织好这些对象，复杂项目有时会用框架管理这件事。
但仅仅把 db 传进来，并不保证事务、权限或错误处理已经正确；这些仍需看实际实现。

评审点：先解释职责怎样分开，交代代价与边界；不把“传入一个对象”升级成项目使用了某框架。

## 7. JWT 签名与加密（jwt）

用户：JWT 里面的内容能看见，怎么还能用来验证身份？

JWT 的签名主要用来核对内容有没有被改过，并不负责把内容藏起来。
例如，一份 token 声明“用户是小林”。别人可能读得到这句话，但把“小林”改成“管理员”后，
原来的签名就不再能通过正确的校验。

所以“看得到内容”和“能伪造有效签名”是两件不同的事。
服务端还必须按约定检查签名算法、密钥、过期时间等条件；光把 token 解码出来并不算验证通过。
敏感信息也不能因为有签名就放心放进去。

评审点：聚焦签名与保密的区别，不一开始灌入完整认证架构；不声称某项目已经做好这些校验。

## 8. 连续两轮“听不懂”（rephrase-chain）

来路：用户在读第三组的 a、b 列表例子。上一条只说“两个名字引用同一个可变对象”。

用户：听不懂。

先看 a 和 b 右边有什么。执行完 b = a，这里仍然只有一个列表：

```text
a ─┐
   ├──→ [1, 2]
b ─┘
```

b.append(3) 往这个列表里加一个 3。列表变了，a 和 b 都仍然连着它，所以都看到 [1, 2, 3]。

用户：还是不懂，b = a 到底做了什么？

那先只看 b = a 这一行，暂时不看 append。
在这行之前，a 已经指向列表 [1, 2]。执行这行时，Python 找到 a 指向的列表，再让 b 指向它。

| 时刻 | 名字 a | 名字 b | 列表有几份 |
| --- | --- | --- | --- |
| 执行之前 | 指向 [1, 2] | 还没定义 | 一份 |
| 执行之后 | 指向原列表 | 也指向原列表 | 仍然一份 |

这行增加的是名字 b，没有创建第二份列表。
后面的 append 才会修改那一份列表的内容。

评审点：同一例子连续使用；先换成指向图，再按用户明确指出的 b = a 缩小到一个步骤。
没有把两次“听不懂”解释为用户能力低，也没有要求用户先通过练习。
