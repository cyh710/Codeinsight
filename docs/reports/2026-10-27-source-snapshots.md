# 源码快照与重复失败恢复交付

基线 `5c31de3`；分支 `codex/source-snapshots`；请求 0024 / ADR 0041。用户在故障诊断和方案对齐后授权修改。本地提交，不合主线、不推送，保留 `.zcode/`。

## 问题与结果

原现场有93次工具调用：37次成功、54次 `stale_source`、2次行号越界。搜索旧索引能命中，读取却依赖当前磁盘文件；换行变化也会导致失败。运行时没有记住确定失败的文件，模型不断换行号重读。

本轮将源码阅读统一到内容寻址快照。新建或更新索引会保存原始字节，AI 工具、代码 API 和代码选区使用同一套版本恢复规则。源码改动或目录失效时，已保存的版本仍可读；没有保存过的真实旧版本不会凭片段拼造。

## 实现

- 快照保存在索引库旁的 `sources/<hash-prefix>/<sha256>`，原子写入并核对原始字节哈希。同一内容共享字节；归属按项目、路径和版本验证，不能因缓存中存在某个哈希就跨项目读取。
- 旧索引没有字节快照时，允许尝试 LF/CRLF 的两种标准形式，但候选必须完全命中原哈希。缩进、空格、注释或实际代码改动不会被忽略。合法读取时缓存保存失败会记录日志，仍返回本次核对的内容；新索引保存失败则不发布。
- 复用 `file_snapshot` 的 `source:<hash>` 与 `epoch:<n>` 记录，不改变表结构、不迁移 schema。全量索引替换同一事务发布，失败保留旧索引。增量索引也保存新字节和版本映射。
- 代码端点支持可选 epoch/hash/commit。来源、材料身份、URL、分页和跳行携带 epoch；首次打开的文件会绑定实际读取版本，补齐身份不额外压入浏览器历史。更新索引后旧页签不静默转向新代码。
- 文件与 epoch 从同一条查询取得，返回值不在读取完成后另取最新 epoch，避免并发更新时给旧正文贴上新版本号。
- 同一回合记住 `stale_source` 的文件，不通过换行号重复读取。连续三轮没有新增材料后，使用关闭工具的模型调用整理已有发现并说明缺口；Provider 即使继续给工具调用也不再执行。正常有新材料的分析总轮次仍不限，现有取消和错误流程保留。
- 工具执行前后检查项目索引版本，更新期间的新结果不混进旧回合。确定失败、空结果和重复材料不算新进展；30轮持续获得新材料及超过旧上限后取消都有测试。
- root/health 提供启动时运行代码指纹及重启提示。启动器不静默复用指纹缺失或不同的旧服务，重复打开启动窗口也检查；运行中发现后端代码变化会提示重启。前端也给出具体提示，保留对话和草稿，不自动结束已有用户进程。

## 使用与边界

1. 当前旧后端不会因前端热更新自动加载修改。需要在原启动窗口按 Ctrl+C，再重新运行启动器；本轮没有按 PID 或端口结束它。
2. 当前项目真正改过且没有旧快照的文件，需要通过已有项目菜单更新索引一次。更新成功后会留下完整源码快照；仅换行差异的旧文件可直接恢复，不需要为了这些差异重建。
3. 不新增后台实时全项目扫描。非 Git 文件在阅读时提示实质变化，Git 项目仍按既有提交快照和状态检测工作。自动增量更新不在本轮。
4. 不自动清理快照；历史源码阅读不等于恢复旧版完整符号图。旧记录缺少版本或旧字节无法恢复时明确提示，不偷偷换新版。
