## 5. 推荐的教材结构

### 5.1 保留一种内容，提供多种来路

同一篇文章可以从语言目录、工程问题、前置知识、项目证据进入，正文只维护一份。建议在原有语言目录之外，增加以下专题路线；名称与顺序仍待用户对齐。

| 路线 | 初学者会问什么 | 内容如何连接 |
|---|---|---|
| 把一个仓库运行起来 | 下载后该点什么？两个 Python 为什么装到不同地方？端口占用是什么？ | 终端与路径 → 入口 → 环境与依赖 → 进程/端口 → 配置 → 启动日志 |
| 一次点击怎样得到结果 | 按按钮之后，哪里真的读了数据库？ | 事件与 state → fetch → HTTP → 路由与校验 → 数据访问/事务 → 响应与渲染 |
| 数据为什么丢了 | 刚才还有，切换、刷新或重启后为什么没有？ | 变量与模块 → 组件/容器生命周期 → 浏览器存储 → 后端内存与 SQLite → 保存时机 |
| 报错时怎样找原因 | 最后一行错误是什么？应该看哪个文件？ | 调用栈 → 日志 → 断点与观察 → 最小复现 → 测试与回归 |
| 读懂 AI 工程 | 为什么检索没找到？为什么回答能一段段出现？ | 文档切块 → 关键词/向量检索 → 上下文预算 → 流式协议 → 工具调用 → 评测 |

路线是入口，不是把现有文章机械排成必修课。读者可以从一个问题进入，缺哪块再补哪块。

例如问“SQL 是什么”仍先打开 SQL 入门；想理解 `SELECT` 就去查询章；想知道项目怎么调用它，就进入“请求到数据库”路线并打开有真实位置的项目证据；想解决改表问题，则进入改名/迁移的操作说明。无需先学完 Python 与 Web 才能理解第一段 SQL。

### 5.2 文章之间说明关系，而不只是互相推荐

建议区分“读不懂这里先补什么”“同一机制的另一种情形”“接下来可深入什么”“项目哪里有实例”。普通的 related 列表很难表达这四种关系。

重叠主题也要有分工。例如 `sql-transactions` 负责 SQL 操作、提交与回滚；`db-transaction` 侧重工程事务边界及跨资源问题。保留旧 ID 与有效锚点，通过互链分工，避免为了整顿目录删除旧入口。

这涉及目录与元数据设计，实施时需先写契约请求；本轮没有更改 schema 或 API。

## 7. 防止重新写成 AI 模板的做法

### 7.1 统一证据标准，正文允许有不同的组织方式

基础机制可以从预测输出入手，故障案例可以从症状与证据展开，选型参考适合边界对照表，动手教程应给出完整可运行步骤。它们不需要都包含“定义—用途—原理—三题—总结”。

每篇写之前，应能回答：读者在什么场景会点进来？读完能解释或处理哪个具体问题？示例在哪里运行、预期是什么、结论在哪个条件下失效？这些用于作者检查，不强制变成正文中的固定段落。

避免用换故事制造差异，也不要为了看起来丰富刻意打乱顺序。题目是否需要练习、练几道、要不要表格，都由学习点决定。

### 7.2 长文的长度应来自推理和观察

保留用户确认的教材级中文长文，但篇幅用于解释中间过程：变量何时改变、请求何时发出、哪份数据仍然存在、哪个边界导致结论变化。减少反复换说法的定义、无必要的比喻和“实际项目很重要”式段落。

第一处解释清楚术语，后续正常使用；不能每节重新入门。章节之间应有递进，也允许读者从检索命中的章节独立读懂关键上下文。

### 7.3 示例应可核对，项目事实单独绑定证据

- 教学示例给出运行条件、必要文件与预期输出；连续项目需要维护共同版本。
- 输出、练习答案和 SQL 结果实际执行核对；故意报错也要明确预期错误。
- 对版本、数据库方言及环境相关的结论标明适用范围。
- 对关键技术断言链接到具体官方章节，不能只挂一个大而全的教程首页。
- 项目实例绑定提交、版本和真实位置。没有证据就只写教学例子，不能补造项目调用链。
- 作者侧运行示例属于内容质量验证，不代表要给产品增加在线代码执行器。

现有来源有作者、地址、许可、快照哈希等记录，应保留。快照哈希只能说明记录的来源版本，不能证明改写后的示例或断言正确。

## 8. 三篇不同体裁的样章设计

以下是完整的组织意图，尚未编写正文，用来避免下一轮再次批量套模板。

### A. 基础解释：函数已经打印了结果，为什么拿到的是 None？

让读者先运行当前商品总价函数，只看屏幕会觉得它成功了。随后把调用结果交给下一段代码，暴露 `None`。并排追踪“屏幕上写了什么”和“调用者拿到什么”，再替换成 `return` 并观察差别。

以 `12 / 36 / 36` 解释默认参数、位置参数与关键字参数；把“相同写法”改为有条件的比较。最后沿调用处读一小段工程代码，区分返回值、日志与副作用。只有能验证这几个区别的练习才保留，不预设题目数量。

这篇保留长文，但主线是一个误解被逐步澄清，不再靠逐项列函数知识来填满章节。

### B. 故障调查：打开材料后，项目和对话列表为什么会变空？

从用户看到的现象开始，把两个独立原因分开：数据容器真的换成空容器；数据还在，但侧栏被遮罩点击关闭。

使用 [ADR 0026](D:/yy2/CodeInsight/docs/decisions/0026-hot-state-and-sidebar-scrim.md) 已有复现记录：热更新后项目 4→0、对话 3→0，且初始化请求未再次发生；另一种情形数据未变，只是左栏不可见。由证据推导为什么应检查模块与 store 身份，以及点击命中元素，而不是统一归因于 React state。

再比较渲染、卸载、HMR、刷新四种事件：哪些对象会重建，哪些数据需要恢复。读者可以跳去 React 状态身份、模块缓存、持久化等文章补课。

正式作为“本项目案例”发布时，要绑定可读取的提交和源码证据。目前修复仍在未提交工作区，不能把它假装成当前索引已经覆盖的代码。

### C. 参考对比：数据存在内存、localStorage、IndexedDB 还是 SQLite？

以同一份草稿分别经历重渲染、组件卸载、网页刷新、后端重启、换浏览器/数据目录来对照。表格说明保存位置、读写方式、生命周期和失败处理，正文解释为什么“页面还显示”不等于“数据已经保存”。

再说明 React state 是 UI 状态机制，IndexedDB 是浏览器存储，SQLite 是数据库；它们可以协作，不能只按“哪个更高级”排序。同步/异步接口、事务、体积与跨端边界按需要展开，不强加一个贯穿故事或三道练习。

这篇帮助用户查边界，A 篇帮助理解机制，B 篇帮助学会查证。体裁差异来自用途差异。

## 9. 内容扩充时需要遵守的技术边界

- 正文的稳定 ID、章节锚点与版本已用于链接、检索、阅读上下文及选区。改写不能只顾文案，把旧入口一起破坏。
- [解析器](D:/yy2/CodeInsight/src/codeinsight/cognitive/concepts/library.py:28) 目前读取带稳定锚点的二级标题；`sources`、`related`、`self-check` 不进入搜索。稳定元数据可以统一，正文不必统一套路。
- 知识上下文按整节纳入，默认预算 12000 字节。丰富长文应适当划分可独立理解的章节，避免一个巨型小节挤掉其余知识；不必按统一字数切碎叙述。
- 本轮扫描最大的章节约为 6571 字节。当前不是“整篇长文都送模型”；未来扩充仍要测试选中章节、检索片段与预算的关系。
- 新增 JS/TS 教材不等于自动获得对应语言的工程实例检测。现有 20 个工程概念检测与源码解析能力，需要单独评估和验证。
- 知识更新、旧链接、语义版本与检索结果要一起检查；不能用多加别名把不存在的内容伪装成命中。

## 10. 推荐下一步与验收

| 选择 | 交付方式 | 代价与判断 |
|---|---|---|
| 先做样章与路线，推荐 | 修已知错误，做上面三种体裁样章和一条学习路线，用户看完再扩 | 首批篇数增加较慢，但能尽早确认质量与风格，减少批量返工 |
| 只扩现有语言章节 | 按 Python/React/SQL 等补新主题 | 目录更满，但运行、排障与跨层理解仍有断点 |
| 一次大批量扩库 | 同时覆盖环境、后端、调试、底层与 AI 工程 | 审校负担大，容易复现模板化与细节错误，不推荐 |

推荐阶段顺序：已知错误与来源定位 → 三篇样章 → 一条可走通的专题路线 → 按缺口小批扩充 → 再复查检索和关联。

验收不只计算文章数量，应包括：

1. 示例输出与答案可以重现；方言、版本和资料出处相符。
2. “完全不懂”的问法能进入正确教材；弱相关片段不能冒充完整覆盖。
3. 路线中的前置知识实际存在，跳转不悬空；教学例子与项目事实清楚区分。
4. 三种样章的组织方式适合各自问题；检查是否又退回同一套段落和固定题数。
5. 找初学者走通至少一条路径，记录停顿与误解。自动执行通过只能证明示例行为，不能代替“人读懂了”。
