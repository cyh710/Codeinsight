# SQL 是什么：数据库、表、行与列

## 先建立直觉 {#overview}

学完这一篇，你能建一张自己的表，插进几条数据，然后问出你想要的那几行。

你有一个记事本，记着每样东西的名字和价格。写着写着发现：按价格排序很难、算总价要手动加、找重复的名字要一行行看。

数据库就是**专门替你做这类事的数据容器**，SQL 是你对它说话的语言。你描述"我要什么"，它负责"怎么拿到"。

先把表想成一张有固定列的电子表格：每一行是一条记录，每一列描述一个属性。这个类比够用，但有两处不一样——数据库会**保证**某些规则（比如两行不能有同一个编号），也会**同时**被很多人读写而不乱。

## 跟着例子理解 {#example}

打开你的终端，建一个数据库文件（这里用 SQLite，它不需要装服务器）：

```bash
sqlite3 shop.db
```

进去之后，我们建一张商品表：

```sql
CREATE TABLE products (
    id     INTEGER PRIMARY KEY,
    name   TEXT    NOT NULL,
    price  REAL    NOT NULL
);
```

注意现在**表是空的**——`CREATE TABLE` 只是定好了结构（有三列、编号不能重复、名字和价格不能为空），还没有任何一条商品。

插两条进去：

```sql
INSERT INTO products (id, name, price) VALUES (1, '笔记本', 12.00);
INSERT INTO products (id, name, price) VALUES (2, '钢笔', 35.00);
```

现在问出你想要的：

```sql
SELECT name, price FROM products WHERE price < 20;
```

你应该看到：

```
name     price
-------  -----
笔记本   12.0
```

**这就是一个完整的数据库会话**：建表 → 填数据 → 查询。剩下的一切都是这三步的组合。

## 一步一步读懂 {#walkthrough}

**第一步，`CREATE TABLE` 定结构。** `id INTEGER PRIMARY KEY` 里的 `PRIMARY KEY` 是主键，它保证每行的 `id` 都不重复且不为空；`NOT NULL` 表示这一列必须有值。这两条不是描述，是**约束**——数据库会替你盯着，违反了会直接报错，而不是等你写代码时才发现。

**第二步，`INSERT` 加数据。** 注意我们把列名写在了括号里：`INSERT INTO products (id, name, price) VALUES (...)`。写列名比不写安全——以后你给表加了新列，不写列名的旧语句会把新列填成默认值或报错。

**第三步，`SELECT` 拿结果。** 这句拆开看：

| 部分 | 作用 |
|---|---|
| `name, price` | 我要看哪几列 |
| `FROM products` | 从哪张表 |
| `WHERE price < 20` | 只留下满足条件的行 |

顺序是固定的：`SELECT` 写在最前，但它描述的是**最后**的结果——先说"我要什么"，再说"从哪来"、"条件是什么"。

**现在动手改一改。** 把 `price < 20` 换成 `price >= 20`，再跑一次：

```
name     price
-------  -----
钢笔     35.0
```

把 `SELECT name, price` 改成 `SELECT name`，再跑一次——这次只回名字，价格那一列不见了。

这两个小改动说明了一件事：**SQL 描述的是"需要什么结果"，不是"怎么执行"**。数据库自己决定用不用索引、先扫哪张表。你只管说清需求。

## 原理与执行过程 {#mechanism}

刚才每一步背后其实都有个设计选择，这里补上——**先会用，再理解为什么**。

`CREATE TABLE` 定结构时，数据库同时记下了这张表的**模式**（schema）：有哪些列、每列什么类型、哪些约束。模式一旦定下，数据库就能拒绝形状不对的数据，而不是等你的程序去处理异常。这也是为什么 `INSERT` 写错列名会直接报错，而不是悄悄写进错误的列。

`SELECT` 的执行顺序**不是**你写的顺序。数据库会先解析你的语句（检查表和列是否存在），再改写成它的内部执行计划（可能用索引，也可能全表扫），最后才执行。`SELECT` 写在最前只是**语法**上的约定——你描述结果，数据库决定怎么拿。

`WHERE price < 20` 里的 `price` 是**列**，`20` 是**字面量**。条件里还可以写表达式和函数，比如 `WHERE price * 2 < 30`（给所有商品打八折后还低于 30 的）。数据库能优化一部分表达式，但把计算写进 `WHERE` 意味着它可能无法用索引——**要按价格过滤，通常是先筛原始列**。

`SQL` 是**声明式**语言：你说"要什么"，不说"怎么做"。这是它能被数据库优化器优化的前提——同一个查询，索引、统计信息、数据量不同，数据库会选不同的执行计划，但你不用改代码。

## 常见误解 {#pitfalls}

**"结果看起来像表格，所以有顺序。"** 没有。除非你写 `ORDER BY`，否则返回顺序**不保证**——同一条查询跑两次可能给出不同顺序。需要稳定顺序就明写：

```sql
SELECT name, price FROM products ORDER BY price;
```

**"`NULL` 就是空字符串或 0。"** 不是。`NULL` 表示**缺失或未知**——某人没填地址、某商品还没定价。它和空字符串、0 都不同，因为"没填"和"填了但是 0"是两件事。用 `WHERE price IS NULL` 找它们，用 `= NULL` 找不到任何东西。

**"数据库就是 SQL 的另一种叫法。"** 不是。SQL 是**语言**，PostgreSQL、SQLite、MySQL 是**数据库系统**——它们说同一种语言，核心语法相通，但各有扩展（SQLite 没有某些类型，PostgreSQL 有额外的语法）。写 SQL 之前得知道你面对的是哪个系统。

**"表就是个文件。"** 不完全是。数据库内部**可能**就用文件存数据，但它对外提供的是查询、约束、事务这些能力——你不用自己一行行扫文件。反过来，数据简单到不值得引入数据库时，普通文件也完全够用。

## 工程中的取舍 {#tradeoffs}

关系型数据库适合**需要结构化查询、有约束、要多条记录保持一致**的场景：订单、商品、用户、账目。

代价是真实的：改表结构要迁移、索引要维护、连接和备份要有人管。数据量小、访问模式简单的时候，一个 JSON 文件可能更省事。

**现在你可以自己判断一次**：把上面的 `products` 表想成你项目里的某个数据。如果它只有几十行、字段固定、只按主键查——一个字典加一个列表就够了，不必上数据库。如果它有几千行、多个程序同时写、还要按不同条件查——那数据库替你解决的正是"同时写不乱"和"别自己扫文件"这两件事。

读项目代码时，先问**它实际保存哪些数据**，再追**读写路径**（谁写、谁读、什么时候写），比先背数据库术语有用得多。

## 自测 {#self-check}

先自己想一想，再往下看答案。

**第 1 题**：你想查出所有价格不低于 20 的商品名，SQL 怎么写？

> **答案**
>
> ```sql
> SELECT name FROM products WHERE price >= 20;
> ```
>
> 条件写在 `WHERE` 后面，比较符是 `>=`（大于等于）。`>= 20` 会把正好 20 的也包含进来。

**第 2 题**：`SELECT * FROM products;` 里的 `*` 是什么意思？生产代码里能不能这么写？

> **答案**
>
> `*` 是"所有列"。读的时候方便，但生产代码里不推荐——表的结构一变，这条查询的返回列就跟着变，调用方的代码可能因此出错。**明确写出需要的列**更稳妥。

**第 3 题**：你想把 `products` 表改名成 `goods`。为什么不能直接 `RENAME`？

> **答案**
>
> SQL 标准里没有直接的 `RENAME TABLE`。通常的做法是：建新表 → 搬数据 → 删旧表 → 改外键指向。三步都做完才算改完——中间任何一步失败，数据都可能对不上。
>
> 这正是"改表结构要迁移"的具体含义。
