# 列表刚才还在：从一次状态丢失调查理解数据生命周期

## 看到空列表，先不要急着重建数据 {#symptom}

列表突然变空，可能是数据真的丢了，也可能只是界面没有显示。这篇沿一次已经记录的事故，区分状态容器、界面可见性、刷新与持久化的边界。

当时的现象是：打开材料后再隐藏，项目或对话列表有时消失。单凭这个描述，很容易把原因归到材料开关上。然而“先做了 A，随后看见 B”只给出了复现线索，没有证明 A 清空了数据。调查必须把数据、界面与中间发生的事件分开。

这是 CodeInsight 自身的历史事故复盘，依据本仓已提交的诊断记录，**不代表当前打开的任意项目也存在相同缺陷**。可在本仓查看固定记录：

```bash
git show 997b90d:docs/decisions/0026-hot-state-and-sidebar-scrim.md
```

## 两种“空了”，证据并不相同 {#evidence}

调查在隔离源码副本中复现了两个原因：

| 观察 | 数据层 | 界面层 | 支持的判断 |
|---|---|---|---|
| 热更新项目状态模块后，项目数量从 4 变 0 | 新状态容器为空 | DOM 中项目行也消失 | 需要检查容器身份与初始化 |
| 热更新对话状态模块后，对话从 3 变 0 | 新容器为空，初始化请求没有再次发生 | 后续材料开关不能恢复列表 | 不是单纯重新绘制的问题 |
| 窄窗口点击材料关闭位置 | 项目和对话数量没有减少 | 命中左栏遮罩，左栏隐藏而材料仍在 | 应检查点击命中与层叠边界 |

第三行不支持“数据丢失”的结论。前两行也不能仅凭现象推断数据库被清空：数据库与浏览器里的状态数组不是同一份东西。

如果不区分它们，可能出现两种无效修复：给隐藏的列表重新请求数据，或者为已经换掉的空容器反复调整 CSS。先确认哪一层变了，才知道下一步该观察什么。

## 数据到底放在哪里 {#ownership}

下面的树按应用职责分类，表示逻辑归属，不表示物理内存布局。先找到数据属于哪一侧，再判断一次操作会越过哪个生命周期边界。

![页面内存、浏览器存储、后端内存与数据库文件属于不同生命周期；页面刷新和后端重启影响的对象不同。](/knowledge/assets/state-storage-boundaries)

组件 state 和共享 store 都可能在页面内存中，但身份与生命周期不完全一样：组件状态与 React 树中的位置等因素有关；模块级容器还受模块如何加载和替换影响。将所有状态问题都解释为 useState 或 key，会漏掉后者。

localStorage 与 IndexedDB 保存到浏览器管理的存储。写入成功后可以跨刷新读取，但受同源、浏览器配置和清理等条件限制，也不意味着网页自动完成恢复。SQLite 通常是后端读取的数据库文件；能否找回历史，还取决于是否打开同一数据目录、事务是否提交以及文件是否可用。

## 为什么热更新能得到一个新的空容器 {#hmr}

开发服务器可以在不整页刷新的情况下更新模块。如果模块顶层每次都新建状态，而初始化只在应用启动时执行一次，就可能出现下面的组合：旧页面仍在，新模块却导出一个空对象，且没有再次加载列表。

下面用普通对象说明身份问题，它不是整个状态库的实现：

```js
function createState() {
  return { projects: [], draft: '' };
}

const first = createState();
first.projects = ['项目 A'];
const second = createState();
console.log(first === second); // false
console.log(second.projects); // []
```

旧对象里的项目没有自动复制到新对象。如果组件开始订阅 second，看到的就是空数组。把 first 改得再正确，也不会改变 second。

Vite 提供 `import.meta.hot.data` 在同一路径模块的连续 HMR 实例间保留数据。这个机制与磁盘持久化不同：它不保证整页刷新后保留，也不应被当作用户历史的权威存储。

![模块重新执行时，新建空 store 会丢失原容器身份；复用 hot.data 中的既有 store，才能继续使用原状态及其闭包。](/knowledge/assets/state-hmr-identity)

本次修复保留完整容器，包括进行中请求与订阅所依赖的闭包，而非只把数组拷回去。代价是状态模块自身的逻辑更新需要手动刷新后加载；组件和样式仍能热更新。这个取舍在固定诊断记录里说明，不能把它包装成所有应用都适用的万能方案。

生产构建没有同样的开发 HMR 流程。如果线上刷新丢草稿，应继续查草稿是否保存和恢复，而不能直接套用 hot.data 修复。

## 同样叫“重新来一次”，边界却不同 {#events}

| 事件 | 常见变化 | 不应直接推断什么 |
|---|---|---|
| React 重渲染 | 组件函数再次计算 UI | 不能推断所有 state 被清空 |
| 组件卸载后再挂载 | 组件对应状态可能重建 | 不能推断模块级 store 或数据库被删除 |
| 开发期模块替换 | 某些模块重新执行，框架可能保留部分状态 | 不能保证任何顶层对象身份都会保留 |
| 网页刷新 | 页面内存重建，重新运行初始化 | 不能保证此前异步保存已完成 |
| 后端进程重启 | 后端内存对象重建 | 不能推断浏览器存储和数据库文件消失 |

React 状态身份还与组件类型、树中位置、key 等有关，详见[组件与 JSX](/learn/react-components)和[State](/learn/react-state)。阅读时应先确认对象归谁管理，再讨论“重建”的含义。

## 保存成功与恢复成功是两件事 {#persistence}

如果希望刷新后保留草稿，完整路径至少包括：选择保存位置、执行写入、处理写入失败、重开后读取、把读到的数据装回正确会话。只实现其中一半，页面仍可能显示空草稿。

| 保存位置 | 网页刷新后 | 后端重启后 | 额外条件 |
|---|---|---|---|
| 前端内存 | 通常重建 | 页面未刷新时可能仍在 | 对象身份仍有效 |
| localStorage / IndexedDB | 可以重新读取 | 浏览器数据仍在 | 同源、成功写入、未被清理、实现恢复 |
| 后端内存 | 可重新向仍在运行的服务请求 | 通常丢失 | 进程仍在且接口可读 |
| SQLite 文件 | 可经接口重新读取 | 使用同一文件时可读 | 事务提交、文件可用、路径一致 |

这个表假设已完成保存。存储配额、权限、错误与事务失败仍需单独处理。IndexedDB 的写入是异步的，发起写入不等于事务已经成功；SQLite 也不能靠“页面出现文字”来证明提交。

这解释了为什么“显示已保存”应当由真实保存结果驱动，而不是在按钮点击时立即显示。它同样解释了为什么服务改用另一个相对路径的数据目录时，看上去可能像历史丢了，其实打开的是另一份数据库。

## 怎样沿证据继续查 {#diagnosis}

不需要同时检查所有层。先选一个具体对象，例如当前项目数组，然后按观察逐步缩小范围：

1. 看数组长度、当前项目 ID 和对象身份，区分数据变化与界面变化。
2. 看请求是否发出、是否成功，核对响应是否写回了同一个容器与会话。
3. 若数据仍在，检查可见性、布局以及实际点击命中元素。
4. 若只在刷新后丢失，再查写入完成、存储位置和恢复流程。
5. 固定复现步骤，区分开发环境与生产环境；修复后验证原路径和相邻路径。

可以用 `python knowledge/learning/examples/state_lifetime.py` 运行一个最小身份模拟。它只验证“两个新对象不会自动共享状态”，不模拟 Vite、React 或整个工作台；真实 HMR 与遮罩问题需要对应浏览器回归。

这里没有通用的“重新请求一下就好”。若旧请求在切换后回写错会话，即使有数据库也会出现错误内容；若容器正确但界面遮罩挡住按钮，也应修命中范围。根因决定修复位置。
