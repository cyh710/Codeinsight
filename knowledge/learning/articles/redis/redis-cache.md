# Redis 缓存：复用可以重建的结果

## 每次请求都要等三秒 {#slow-request}

读完这一篇，你能手写一个带过期时间的缓存，知道键里该放什么、TTL 怎么定，以及缓存失效时数据库为什么会被打垮。

商品详情页每次请求都要查库、算价格、拼推荐，一次 3 秒。同一个商品被看 100 次，就重算 100 次。

缓存做的事只有一句：把算过的结果放在旁边，下次先看旁边有没有。

Redis 是把这个"旁边"搬到另一个进程，让多个服务共享。它不改变缓存的逻辑。

## 用字典和过期时间做一个缓存 {#handmade-cache}

先不管 Redis，用标准库写一个最小版本，新建 `cache_demo.py`：

```python
import time

CACHE = {}
TTL = 60
clock = {"now": 100.0}
db_calls = {"count": 0}
PRODUCTS = {7: {"name": "机械键盘", "price": 499.0}}


def now():
    return clock["now"]


def load_product(pid):
    db_calls["count"] += 1
    time.sleep(0.2)  # 假装这是一次查库
    return dict(PRODUCTS[pid])


def get_product(pid):
    key = f"product:{pid}:v1"  # 结构变化时换成 v2，旧缓存自然失效
    entry = CACHE.get(key)
    if entry is not None and entry["expires_at"] > now():
        return entry["value"], "命中"
    value = load_product(pid)
    CACHE[key] = {"value": value, "expires_at": now() + TTL}
    return value, "未命中，已回填"


def update_price(pid, price):
    PRODUCTS[pid]["price"] = price
    CACHE.pop(f"product:{pid}:v1", None)  # 先写库再删，避免回填旧值


print(get_product(7))
print(get_product(7))
update_price(7, 399.0)
print(get_product(7))
clock["now"] += TTL + 1
print(get_product(7))
print("查库次数:", db_calls["count"])
```

运行：

```bash
python cache_demo.py
```

你应该看到：

```
({'name': '机械键盘', 'price': 499.0}, '未命中，已回填')
({'name': '机械键盘', 'price': 499.0}, '命中')
({'name': '机械键盘', 'price': 399.0}, '未命中，已回填')
({'name': '机械键盘', 'price': 399.0}, '未命中，已回填')
查库次数: 3
```

`load_product` 里用 0.2 秒代替真实的三秒，不然每次跑例子都要等半天。第二个返回值是例子为了让你看见命中情况加的，真实函数通常只返回商品。

第一次未命中，回源并回填。第二次还在 60 秒内，直接拿缓存，没有查库。`update_price` 改了数据库并删掉缓存，所以第三次又回源，拿到新价格。时钟拨过 61 秒后，第四次发现缓存过期，再回源一次。`查库次数: 3` 就是这三条路径的证据。

## 读路径与写路径 {#read-write-path}

**读路径按顺序做五件事。** 先拼出缓存键，再用它去查；查到且没过期就返回；没查到就回源；把结果和过期时间写回去；再返回。

键是 `product:{pid}:v1`。`v1` 是结构版本：今天缓存的值是 `{name, price}`，明天响应里多了 `stock`，旧缓存里没有这个字段，读代码可能直接报错。把前缀换成 `v2`，旧键自然不再命中，过期后消失，不需要扫描删除。

如果结果和用户有关，比如"我的订单"，键里必须带用户 id 或权限范围；和语言有关就带 `locale`；和租户有关就带 `tenant`；调用模型时，模型名和提示版本也要进键。漏一个维度，A 的结果就可能被 B 拿到，或者新模型读到旧模型的输出。这不是命中率问题，是数据泄露或错误答案。

判断命中时用 `entry is not None`，因为 `CACHE.get` 在键不存在时返回 `None`。如果缓存值本身可能是空字符串、0、空列表，甚至 `None`（表示"这个 id 不存在"），更不能写 `if not value`；例子包了一层 `entry`，就是为了让"键存在但值是空"和"键不存在"分开。空值也可以缓存，但要给一个较短的 TTL，否则每次请求都会穿透到数据库。

**写路径先改数据库，再删缓存。** 顺序反过来会多一个窗口：缓存先删了，某个请求立刻未命中，读到还没更新的旧值，又把旧值写回缓存；等数据库更新完，缓存里已经是旧的。

删缓存而不是直接写新值，是因为并发下"写入新值"和"另一个请求回填旧值"可能交错，最终留下谁取决于时序。删除更简单，下一次读自然会回源。代价是下一次读会慢一点。

删除也消不掉所有竞争。一个请求未命中后读到旧值，另一个请求更新了数据库并删了缓存，第一个请求再把旧值写回去，缓存就旧到 TTL 为止。常见的缓解是缩短 TTL、延迟双删、用版本号让旧键失效，或者在回填前核对数据库版本。**缓存一致性不是"删了键就绝对一致"，而是把不一致的窗口缩短，并给它一个上限。**

如果数据会派生出多个缓存键，比如详情页和列表页各一份，只删一个不够。可以让这些键共享一个版本前缀，改数据时把版本加一，整族键一起失效。

## 把它搬到进程外就是 Redis {#to-redis}

字典版有三个限制：只在当前进程；重启就没了；多副本各有一份，互不一致。Redis 把存储搬到进程外，多个进程连同一个实例，看到同一份缓存。

先装客户端：

```bash
pip install redis
```

下面的代码需要本机有 Redis 服务（默认端口 6379）。没有服务也能读懂，逻辑和上一段一样，只是 `get`、`set` 换成了网络调用。把上一段的 `PRODUCTS` 和 `load_product` 也放进同一个文件，这段就能直接运行：

```python
import json
import redis

r = redis.Redis(host="localhost", port=6379, decode_responses=True)


def get_product_redis(pid):
    key = f"product:{pid}:v1"
    raw = r.get(key)
    if raw is not None:
        return json.loads(raw), "命中"
    value = load_product(pid)
    r.set(key, json.dumps(value), ex=60)
    return value, "未命中，已回填"


def update_price_redis(pid, price):
    PRODUCTS[pid]["price"] = price
    r.delete(f"product:{pid}:v1")
```

`ex=60` 让 Redis 自己删键。不要在值里再存一个 `expires_at` 让应用判断：Redis 的过期在服务端执行，客户端时钟不可信，也不需要在每个读者那里重复判断。

`decode_responses=True` 让 `get` 返回字符串。不设的话返回 `bytes`，`json.loads` 也能处理，但和字符串混用容易出错。存进去之前要明确序列化格式；Python 对象不能直接塞进 Redis，`json.dumps` 是最省事的一种。

| 动作 | 字典版 | Redis |
|---|---|---|
| 读 | `CACHE.get(key)` | `r.get(key)` |
| 写并设过期 | 存值加 `expires_at` | `r.set(key, value, ex=60)` |
| 删 | `CACHE.pop(key, None)` | `r.delete(key)` |
| 共享范围 | 当前进程 | 所有连上来的进程 |

Redis 读写走网络，比字典慢，换来的是共享和跨进程一致。它也会超时、连不上、被清空，代码要把"缓存不可用"当正常分支，而不是假设它永远在。

## 过期时间该定多长 {#ttl-choice}

TTL 是两个约束的交点：数据多久变一次，以及你能忍受多旧。两个答案取更小的那个，再留一点余量。

| 数据 | 起点 | 原因 |
|---|---|---|
| 商品价格 | 30–60 秒 | 变价不频繁，短暂旧价可接受 |
| 用户权限 | 不缓存，或 10–30 秒 | 封号、降权要尽快生效 |
| 汇率 | 1–5 分钟 | 上游更新频率有限 |
| 首页报表 | 5–60 分钟 | 计算贵，旧一点没关系 |

这些数字是起点，不是标准答案。上线后看数据实际变化频率和用户投诉，再调。TTL 短，命中率低、回源多；TTL 长，命中率高但旧值窗口大。你是在命中率和新鲜度之间选一个位置，不存在两边都满分。

别设永不过期，除非数据真的不可变。不可变数据也应该带版本号，换版本时换键，这样旧值不会永远占着内存。

滑动过期要小心：每次命中都续期，热门键可能永远不过期。业务不能接受长期旧值时，加一个绝对上限，比如"无论多热，写入后最多活 10 分钟"。

同一批键同时写入、TTL 又一样，会在同一秒一起过期。给 TTL 加一点随机抖动，比如 `ex=60 + random.randint(0, 30)`，把失效时间摊开。

不存在的 id 也要缓存。每次查一个不存在的主键都绕过缓存打到库，这叫穿透。把"不存在"这个结果缓存 30 秒，能挡住大量重复请求；如果 id 空间很大且攻击明显，再考虑布隆过滤器：用一小块内存判断"这个 id 一定不存在"，挡住绝大多数无效查询。

## 热键过期时会发生什么 {#stampede}

热门商品的键一过期，1000 个请求同时未命中，1000 个都去查库。数据库平时只接 10 个查询，这一刻直接被打满。这是缓存击穿。

大量键同时过期，或者 Redis 整个挂了，叫失效风暴，也叫雪崩。两者的共同点是：缓存本来在挡流量，失效瞬间流量全落到后端。

三种常见缓解：

1. 单飞锁。第一个未命中的请求去抢锁，抢到才回源；其他请求等结果或短暂重试。Redis 用 `SET lock:key token NX EX 10` 抢锁，释放时校验 token，避免删掉别人后来续上的锁。锁必须带过期时间，进程崩了才不会永久锁死。
2. 逻辑过期加后台刷新。缓存值里带一个逻辑过期时间，到点不立刻删，而是让一个请求去刷新，其余请求先拿旧值。用户看到的是有上限的旧数据，但不会一起去打数据库。
3. 抖动和预热。TTL 加随机数，避免同时失效；发布后先预热热点键，别让冷缓存直接接全量流量。

把 TTL 调长只是把问题推远，不是解决。锁也会带来排队和新的失败模式，必须有超时和降级。

如果 Redis 挂了，回源之前先问一句：数据库能不能承受这份流量？承受不了，返回 503 或继续供旧值，可能比把数据库打挂更好。

## 有 Redis 不等于有缓存 {#cache-premise}

缓存的前提是：**里面的东西能根据权威数据重建。** 丢了、清了、重启了，系统仍然正确，只是变慢。如果丢了就丢数据，那它是存储，不是缓存。

**"项目连了 Redis，就说明有缓存。"** Redis 也常被用来做队列、计数器、限流、分布式锁。缓存需要一条完整的读写路径：读时先查它，未命中回源，写时失效。只看到 `r.set`，可能只是在保存状态。

**"缓存可以当数据库用。"** 如果 Redis 是唯一副本，淘汰、重启、误删 `FLUSHALL` 都会让数据消失。Redis 的持久化不能替代事务、约束、备份和审计。订单、余额这类权威数据，主副本必须在数据库。

**"缓存键不用带用户。"** 结果依赖身份、权限、租户或语言时，这些维度必须进键，或者干脆别缓存。漏掉用户维度，A 的页面可能显示 B 的数据；这是安全漏洞，不是命中率问题。

**"Redis 挂了，服务就该跟着挂。"** 缓存按定义是可选的。回源、返回旧值、快速失败 503，三种策略各有代价。回源可能压垮数据库，快速失败可能让本来能服务的请求全挂。选一个，测过，写清楚。

**"设了 TTL 就不用管失效。"** TTL 只给旧数据封顶，不保证写完立刻正确。用户改了昵称，刷新后还要等 60 秒才看到，这是产品缺陷。写路径要删缓存，TTL 是兜底。

## 练习 {#self-check}

**第 1 题**：TTL 是 60 秒，在 t=0、t=30、t=61 各请求一次同一个商品，数据库会被查几次？

> **答案**
>
> 两次。t=0 未命中，回源一次并回填；t=30 命中，不查库；t=61 已过期，再回源一次。
>
> 如果 t=30 那次也触发了滑动续期，过期时间会往后推，t=61 可能仍然命中。所以 TTL 怎么算，要先确定是固定过期还是滑动过期。

**第 2 题**：为什么先更新数据库、再删缓存，而不是反过来？

> **答案**
>
> 反过来会多一个窗口：缓存先删掉，某个请求立刻未命中，读到还没更新的旧值，又把旧值写回缓存；等数据库更新完，缓存里已经是旧的。
>
> 先更新数据库再删缓存，能让这个窗口更小。但它不是绝对一致，仍然有并发回填的竞争，所以要靠短 TTL 或版本号给不一致封顶。

**第 3 题**：一个热门商品的缓存键刚过期，1000 个请求同时到达。除了把 TTL 调长，还能怎么做？

> **答案**
>
> 用单飞锁让一个请求回源，其他请求等待或短暂重试；或者用逻辑过期加后台刷新，让其他请求先拿旧值。
>
> 再加 TTL 随机抖动，避免大量键同时到期。把 TTL 调长只是推迟下一次风暴，并没有消除它。
