# HTML：页面的结构与语义

## 一个能双击打开的页面 {#overview}

学完这一篇，你能从空文件写出一个能双击打开的留言板页面，并说清每个标签为什么是它而不是 div。

上一篇的留言板用 JavaScript 发了请求。这一篇先不管请求，只把页面本身写对：一个输入框、一个提交按钮、一列留言。

新建一个 `index.html`，双击它，浏览器就会打开，不需要服务器。浏览器对 HTML 很宽容：标签写错、结构缺一块，它也会尽量画出东西。宽容让上手变快，也让“能显示”和“写对了”经常被混为一谈。

## 从一行大标题加到一列留言 {#build-page}

**先放一行标题。** 新建 `index.html`，只写这一行：

```html
<h1>留言板</h1>
```

保存，双击。你会看到一行又粗又大的“留言板”，标签页上写的是文件名 `index.html`。

这行字能显示，是因为浏览器自动补出了 `html`、`head`、`body`。但它没有声明字符集，浏览器只能猜编码，猜错时中文会变成乱码；它也没有页面标题，标签页只好用文件名。能显示是浏览器的容错，不是这段代码完整。

**再补上骨架和表单。** 把文件改成：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>留言板</title>
</head>
<body>
  <main>
    <h1>留言板</h1>

    <form method="get">
      <label for="text">留言内容</label>
      <input id="text" name="text" placeholder="写点什么" required>
      <button type="submit">提交</button>
    </form>
  </main>
</body>
</html>
```

保存文件，回到浏览器刷新。标签页变成“留言板”，页面里出现一行字、一个输入框、一个“提交”按钮。窗口很窄时，标签、输入框、按钮会折成几行，这是正常的。

**加上留言列表。** 在 `</form>` 后面插入：

```html
    <h2>全部留言</h2>
    <ul>
      <li>第一条留言</li>
      <li>第二条留言</li>
    </ul>
```

现在整份文件是：

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>留言板</title>
</head>
<body>
  <main>
    <h1>留言板</h1>

    <form method="get">
      <label for="text">留言内容</label>
      <input id="text" name="text" placeholder="写点什么" required>
      <button type="submit">提交</button>
    </form>

    <h2>全部留言</h2>
    <ul>
      <li>第一条留言</li>
      <li>第二条留言</li>
    </ul>
  </main>
</body>
</html>
```

你应该看到：

```text
浏览器标签页：留言板

留言板
留言内容 [写点什么        ] [提交]
全部留言
• 第一条留言
• 第二条留言
```

没有任何装饰：白底黑字，输入框和按钮是浏览器的默认样式，列表前面有小圆点。那两条留言是写死的占位内容，刷新页面它们还在，因为你还没写任何代码去改它们。

## 每个标签在回答什么问题 {#tags}

浏览器读到 HTML，不是记住一串字符，而是建一棵树。每个标签是一个节点，嵌套关系就是父子关系。F12 打开 Elements 面板，看到的缩进就是这棵树：

```text
html
├─ head
│  ├─ meta
│  ├─ meta
│  └─ title
└─ body
   └─ main
      ├─ h1
      ├─ form
      │  ├─ label
      │  ├─ input
      │  └─ button
      ├─ h2
      └─ ul
         ├─ li
         └─ li
```

树顶的两个分支要分清。`head` 里的东西不显示在页面上：`meta charset="UTF-8"` 决定浏览器按什么编码解释字节，`meta name="viewport"` 让手机按设备宽度排版，`title` 是标签页和收藏夹里的名字。`body` 里才是用户看到的内容。`<html lang="zh-CN">` 告诉读屏和翻译工具这页主要是中文；`<!DOCTYPE html>` 让浏览器用标准模式解析，而不是退回兼容旧页面的怪异模式。

标签的名字在声明“这块内容是什么”，不是“它长什么样”。

`<h1>` 是页面的主标题。浏览器默认把它显示得又大又粗，但大小来自浏览器的默认样式表，可以改；它是主标题这件事，改不了。

`<main>` 标记页面的主要内容区域。读屏软件可以跳过导航直接到这里。一个页面放一个就够。

`<form>` 把一组控件圈在一起，让它们可以一起提交。按回车提交、点击提交按钮后带着数据导航，这些流程由这个容器组织；输入框上的 `required` 也只有在表单提交时才会自动拦截。

`<label for="text">` 和 `<input id="text">` 通过 `for` 与 `id` 连起来。点和读屏都靠这条线。

`<input>` 的 `id` 是它在页面里的名字，`name` 是它提交给服务器时用的字段名。这是两个不同的系统，两个都要写。`placeholder` 是输入前的提示，`required` 表示不填不能提交。

`<button type="submit">` 是一个可操作的按钮。`type="submit"` 说明按它会提交所在的表单；不写 type 时，表单里的按钮默认也是 submit，写出来是为了读代码的人不用猜。`type="button"` 则只响应点击，不会提交。

`<ul>` 和 `<li>` 声明“这是一组并列条目”。浏览器默认画小圆点，但圆点也只是默认样式。

一张表对照：

| 标签 | 它声明的事 | 浏览器因此能做什么 |
|---|---|---|
| `h1` | 页面主标题 | 读屏能列出标题大纲 |
| `form` | 一组要一起提交的控件 | 回车提交、必填校验 |
| `label` | 某个控件的说明文字 | 点文字聚焦输入框，读出名字 |
| `input` | 单行输入 | 键盘输入、自动填充、必填校验 |
| `button` | 可点击的操作 | Tab 聚焦、Enter/Space 触发、提交表单 |
| `ul` / `li` | 一组并列条目 | 读屏报出“列表，共 2 项” |

HTML 说“这是什么”，CSS 说“它长什么样”，JavaScript 说“点它之后做什么”。三者叠在同一棵 DOM 树上。把 CSS 全删掉，这个页面仍然可读、可输入、可提交，因为结构还在。

## 按下提交之后，页面去了哪里 {#submit-flow}

在输入框里写“今天下雨”，点提交。

浏览器先把输入框里的文字和 `name="text"` 拼成一对数据，再根据 `method="get"` 把它编码进地址，向当前页面发一次 GET 请求。地址栏末尾会多出类似这样的一段：

```text
?text=%E4%BB%8A%E5%A4%A9%E4%B8%8B%E9%9B%A8
```

`%E4%BB%8A...` 是“今天下雨”的 UTF-8 百分号编码。不同浏览器显示中文的方式略有差别，但 `text=` 这个字段名一定来自 `<input name="text">`。

然后整页重新加载：浏览器拿到同一份 HTML，重新建一遍 DOM。列表还是那两条写死的内容，输入框通常回到空的，因为新的这份 HTML 里它没有 `value`。列表没有因此多一条，是因为**没有任何代码把地址里的 `text` 变成新的 `<li>`**。表单只负责把数据交出去，不负责把它写回页面。

`required` 在提交前会先检查。输入框空着点提交，浏览器会弹出提示并阻止这次导航。

如果改成 `method="post"`，数据会放进请求正文而不是地址栏，但页面仍然会导航。要真正接收并显示，得有后端读取这个字段、在返回的 HTML 里多渲染一个 `<li>`；或者用 JavaScript 拦住默认提交，自己处理。两条路都不在这份文件里。

默认情况下，双击打开的页面地址以 `file://` 开头。页面能正常显示，但本地文件上的表单提交在不同浏览器里限制不一样。如果点提交没反应，或者地址栏没有出现 `?text=`，就别和浏览器较劲：在文件所在目录运行 `python -m http.server 8001`，再打开 `http://localhost:8001/`。这时提交走的是 HTTP，地址栏的变化更容易观察。

再注意一个细节：浏览器只提交**有 `name`** 的控件。把 `name="text"` 删掉，页面看起来毫无变化，但提交时地址里不会再有 `text=`，服务器也就收不到你输入的内容。

## label 不只是给鼠标用的 {#label-a11y}

点一下“留言内容”这四个字。光标会跳进输入框，因为 `for="text"` 指向了 `id="text"`。

把 `for` 删掉，再点文字。光标不动，输入框完全没有反应。页面看上去一模一样，关联已经断了。`for` 和 `id` 差一个字母，效果就没了。

焦点在页面里时，按 `Tab` 键走一遍：先到输入框，再到提交按钮。焦点在按钮上时，按 `Enter` 或空格会触发提交。这些行为不是你写的，是浏览器给原生表单控件的。

读屏软件靠 `label` 说清这个输入框是干什么的。没有关联时，它可能只读出一个“编辑框”，用户不知道这里该填什么。`placeholder` 补不上这个缺口：一开始输入它就消失，颜色通常很浅，也不是可靠的名称来源。

如果不想用 `for`/`id`，也可以把输入框包进标签里：

```html
<label>
  留言内容
  <input name="text" placeholder="写点什么" required>
</label>
```

这样也能关联，而且不需要 id。显式写 `for`/`id` 的好处是样式和脚本都更容易找到对应关系。

按钮的可访问名称来自按钮里的文字。“提交”两个字既显示给所有人，也读给读屏用户。只有图标的按钮才需要额外的 `aria-label`，这一页用不上。

还有一条和键盘有关的约定：不要在 CSS 里把焦点轮廓直接删掉。键盘用户靠那个框知道自己现在在哪。可以换一个更清楚的颜色，不能让它彻底消失。这一点在讲 CSS 的那篇里还会出现。

## 页面能显示，不代表结构站得住 {#shown-vs-correct}

把上面所有标签换成 `div`，再写一套 CSS 把大小、颜色、间距补齐，页面可以长得一模一样。但按 Tab 的顺序、读屏读出的内容、回车能不能提交，都会变。

**“`h1` 是大字，`h3` 是小字，按外观挑一个。”** 默认字号来自浏览器的样式表，CSS 可以让 `h3` 比 `h1` 还大。标题级别描述的是大纲里的层级。主标题下面直接跳到 `h3`，视觉上可能很合适，读屏的标题列表里却缺了一层。要小字就改 `font-size`，不要改级别。

**“`div` 加个点击事件就是按钮。”** 按 Tab 走一遍就能看出来：`div` 不会被聚焦，按 Enter 或空格也不会触发。读屏不会说“按钮”。它也不能自动提交表单。原生 `button` 把这些都免费给了你；用 `div` 就得自己补 `role`、`tabindex`、键盘事件和焦点样式，补漏一个就少一块行为。

**“`label` 放输入框旁边就行，`for` 可以省。”** 点一下标签文字试试，输入框不会聚焦，读屏也可能不把两者联系起来。用 `for`/`id` 或把输入框包进 `label`，关联才成立。页面里 `id` 还不能重复，重复时 `label` 只会认第一个，后面的输入框就失去了标签。

**“`id` 有了，`name` 无所谓。”** `id` 服务于页面内部：`label` 找它，CSS 和 JS 也找它。`name` 服务于提交：浏览器把它当作字段名交给服务器。把 `name` 删掉再提交，地址里没有 `text=`，后端收不到内容。这两个属性解决两件不同的事。

**“用户输入的内容，用 `innerHTML` 插回页面就行。”** 如果留言是 `<img src=x onerror=alert(1)>`，拼进 `innerHTML` 后浏览器会把它当标签执行，数据就变成了代码。这一页还没有用 JS 插入留言；等你写那一步时，用 `textContent` 放纯文本。显示结构可以手写，用户数据不行。

## 多写一个标签值不值 {#semantic-tradeoffs}

原生元素替你维护了一堆不显眼的行为：Tab 焦点、Enter/Space 触发、禁用状态、表单提交、读屏播报。自己用 `div` 拼一个按钮，省下的是一个标签，欠下的是一串状态。页面越复杂，这笔账越不划算。

反过来，语义不是越多越好。只是为了让两行文字并排而套一层 `div`，没有问题；这个 `div` 不假装自己是按钮或标题就行。每多一层包装，DOM 和 CSS 就多一层要维护的关系。判断标准是“这层在表达什么结构”，不是“多写标签显得正规”。

有个简单的检查：把 CSS 停掉，页面还能不能读、能不能操作？如果能，结构大概率是站得住的。如果一停样式，布局全散、按钮全不能点，说明很多东西只存在于视觉里。

读别人的前端代码时，先看 `main`、标题层级、表单控件，知道这个页面让用户做什么；再去追事件处理函数。从一堆 CSS 类名开始读，通常更慢。类名是给样式用的，结构才说明用户流程。

## 三个结构练习 {#self-check}

**第 1 题**：只写 `body` 里的结构：一个主标题、一个带标签的输入框、一个提交按钮、两条留言。

> **答案**
>
> ```html
> <main>
>   <h1>留言板</h1>
>   <form method="get">
>     <label for="text">留言内容</label>
>     <input id="text" name="text" placeholder="写点什么" required>
>     <button type="submit">提交</button>
>   </form>
>   <h2>全部留言</h2>
>   <ul>
>     <li>第一条留言</li>
>     <li>第二条留言</li>
>   </ul>
> </main>
> ```
>
> `label` 的 `for` 和 `input` 的 `id` 必须一致；`name` 决定提交时的字段名；`button` 的 `type="submit"` 让它提交表单。

**第 2 题**：点提交后，输入的内容为什么没有出现在列表里？地址栏多了什么？

> **答案**
>
> 表单执行的是原生提交：浏览器把带 `name` 的控件编码进地址，向当前页面发 GET 请求，然后整页重新加载。地址栏会多出 `?text=...`，中文被编码成百分号形式。
>
> 列表没变，是因为没有任何代码把地址里的 `text` 变成新的 `<li>`。输入框通常变空，因为新加载的 HTML 里它没有 `value`。要让留言出现，需要后端渲染新页面，或者用 JS 拦截提交并更新 DOM。

**第 3 题**：下面这个“按钮”有什么问题？

```html
<div class="button" onclick="send()">提交</div>
```

> **答案**
>
> 它看起来像按钮，但键盘用户按 Tab 聚焦不到它，Enter 和空格也不会触发，读屏不会说“按钮”，它也不会提交外面的表单。
>
> 换成：
>
> ```html
> <button type="submit">提交</button>
> ```
>
> 如果确实要用 `div`，至少得补 `role="button"`、`tabindex="0"` 和键盘事件，还要处理禁用和焦点样式。这些原生按钮本来就有，补一遍只是在重新实现它。
