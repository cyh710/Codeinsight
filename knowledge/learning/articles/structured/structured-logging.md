# 结构化日志：记录可以关联的事件

## 先建立直觉 {#overview}

日志记录程序在某个时间发生了什么。结构化日志把重要字段独立保存，例如任务 ID、项目 ID、操作类型和耗时，方便筛选与关联。它的价值不在于输出更多文字，而在于能回答具体诊断问题。

## 原理与执行过程 {#mechanism}

日志通常包含级别、时间、来源与业务字段。一次请求跨多个函数时，可用关联 ID 串起事件。记录开始不代表完成，完成日志还应明确成功、失败和不确定结果。异常栈有助于诊断，但用户提示与内部日志可以使用不同细节层次。

## 跟着例子理解 {#example}

以下是独立教学示例，不代表被分析项目的实际代码。

```python
import logging
logger = logging.getLogger(__name__)
logger.info("index_finished", extra={"project_id": 7, "files": 12})
```

默认日志配置可能不显示 INFO 级别。要观察终端输出，需要在应用入口配置相应级别与
handler；这个例子只展示事件名与字段，不承诺已经配置 JSON 输出。

## 一步一步读懂 {#walkthrough}

事件名描述已经结束的索引，extra 保存可独立处理的字段。要真正输出 JSON，还需要配置相应格式器；仅传 extra 不会自动变成 JSON 日志。关联字段的名称和生命周期应统一，才能跨模块查询。

## 常见误解 {#pitfalls}

日志中出现“成功”不能代替实际操作返回状态。不要打印 API 密钥、Cookie、完整令牌或不必要的用户数据。采样、截断和缓冲可能让日志缺失，因此没有某条日志不一定证明路径从未执行。

## 工程中的取舍 {#tradeoffs}

更多日志增加诊断信息，也增加存储、性能和隐私成本。优先记录状态转移、外部调用结果和可恢复错误。指标看整体趋势，日志看具体事件，追踪看跨组件链路，它们可以互补。
