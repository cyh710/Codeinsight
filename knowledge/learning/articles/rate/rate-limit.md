# 限流：保护有限处理能力

## 一分钟一万次请求会发生什么 {#overview}

学完这一篇，你能给接口加上限流，知道自己该按用户、IP 还是全局限额计数，也能看懂 429 响应。

周五下午，一个脚本拿着正常注册的账号，一分钟里往搜索接口打了一万次请求。数据库连接池被占满，其他用户的请求开始超时。日志里每一行都合法：登录过、参数对、没越权。

问题不是请求"合不合法"，而是这个来源出现得太密。限流拦的是频率，不是身份。它保护的是有限的处理能力：连接池里的连接、下游接口的每分钟配额、一台机器能同时跑的查询。

所以先回答一个比"限多少"更早的问题：你在数谁？

## 限的是谁：用户、IP、接口还是全部 {#dimensions}

"每分钟 100 次"这句话本身不完整。没说清 key 是什么，限额就没法落地。

| 计数键 | 挡住谁 | 常用在 | 代价 |
|---|---|---|---|
| 用户 ID | 单个账号刷接口 | 导出报表、发消息、下单 | 一个用户多台设备共享同一份额度 |
| IP | 同一来源的匿名流量 | 登录、注册、发验证码 | 公司、学校、运营商 NAT 下，很多人共用一个出口 IP |
| 用户 + 接口 | 某账号刷某个功能 | 搜索、导出 | key 变多，存储和清理成本上升 |
| 接口 | 所有用户抢同一个入口 | 昂贵的第三方调用 | 一个人就能把整个接口的额度吃光 |
| 全局 | 整个服务或下游 | 支付回调、写数据库 | 一个热点接口可能挤占其他接口的额度 |

登录接口很适合说明 key 选错的后果。只按 IP 限，办公室里几十个人共用一个出口 IP，一个人跑脚本试密码，全公司一起被挡；只按账号限，攻击者换账号继续撞库，每个账号只试几次，永远碰不到阈值。常见做法是两个都算：IP 挡批量尝试，账号挡针对某个人的撞库。

导出报表按用户算。同一个人开三个标签页同时导出，应该共享这 100 次，而不是每个标签页各拿 100 次。

支付回调按全局算。它来自同一个下游，你关心的是"别把数据库写满"，不是"哪个回调账号太活跃"。

**key 选错，数字再准也保护不了你想保护的东西。** 先找出真正会被打满的资源，再决定数谁。

## 手写一个令牌桶 {#token-bucket}

令牌桶只维护两个数：当前有多少个令牌，上次补充是什么时候。每次请求先按流逝的时间补令牌，够 1 个就放行并扣掉，不够就拒绝。

新建 `bucket.py`，不需要装任何第三方库：

```python
import time


class TokenBucket:
    def __init__(self, capacity, rate, clock=time.monotonic):
        self.capacity = float(capacity)
        self.rate = rate
        self.tokens = float(capacity)   # 一开始装满，允许一次突发
        self.clock = clock
        self.last = clock()

    def allow(self):
        now = self.clock()
        # 先按流逝的时间补币，再判断够不够
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False


class FakeClock:
    """假时钟，让输出不依赖机器的运行速度。"""

    def __init__(self):
        self.now = 0.0

    def __call__(self):
        return self.now

    def advance(self, seconds):
        self.now += seconds


clock = FakeClock()
bucket = TokenBucket(capacity=3, rate=1, clock=clock)

for n in range(1, 6):
    ok = bucket.allow()
    print(f"第{n}次请求:", "放行" if ok else "拒绝", f"剩余 {bucket.tokens:.1f}")

clock.advance(2)
ok = bucket.allow()
print("等 2 秒后:", "放行" if ok else "拒绝", f"剩余 {bucket.tokens:.1f}")
```

运行：

```bash
python bucket.py
```

你应该看到：

```
第1次请求: 放行 剩余 2.0
第2次请求: 放行 剩余 1.0
第3次请求: 放行 剩余 0.0
第4次请求: 拒绝 剩余 0.0
第5次请求: 拒绝 剩余 0.0
等 2 秒后: 放行 剩余 1.0
```

真实项目里不要传 `FakeClock`，用默认的 `time.monotonic` 就行。`FakeClock` 只是为了让这篇的输出每次一样。

## 桶里的数字怎么变 {#walkthrough}

第一步，`TokenBucket(capacity=3, rate=1)` 造出一个装满 3 个令牌的桶。`capacity` 是上限，也是允许的最大突发量；`rate` 是每秒补几个。

第二步，每次 `allow()` 都先算 `(now - last) * rate`。假时钟没有前进时，这个值是 0，所以前三次请求各扣 1 个，余额从 3 走到 0。

第三步，第 4、5 次请求时余额不足 1，返回 `False`。被拒绝的请求**不扣令牌**，所以余额仍然是 0。

第四步，`clock.advance(2)` 让时间前进 2 秒。下一次 `allow()` 补进 2 个令牌，扣掉 1 个后剩 1.0。

这里有两个数要分开看：

- **容量决定能突发多少。** 空闲十分钟后突然来 3 个请求，桶里最多也只有 3 个，第 4 个立刻被拒。
- **速率决定长期平均。** `rate=1` 表示长期最多每秒 1 个，不管请求来得多么不匀。

这两个数还容易和并发上限混在一起。限流限制的是单位时间让多少请求进入；线程池大小限制的是同一时刻有多少个正在处理。一个慢查询可以把并发占满，哪怕每秒请求数远低于限额。

这正好是固定窗口做不到的。固定窗口的实现很直白：key 拼上当前分钟，`INCR` 一次，超过 100 就拒绝，第一次请求时给 key 设 60 秒过期。

漏洞在窗口交界。限额 100 次/分钟时：

- 12:00:59 的第 100 次请求用完了 12:00 这一窗。
- 12:01:00 窗口清零，又能进 100 次。

两秒内实际放行了 200 次，是限额的两倍。下游不会感受到"每分钟 100 次"，只会感受到瞬间 200 次。

滑动窗口记录过去 60 秒内的请求时间戳（或把 60 秒切成小格分别计数），任意 60 秒内都不超过限额，边界问题消失。代价是每个用户要存一串时间戳或一组小计数器，内存随流量和 key 数量上涨。

令牌桶不关心"这一分钟"从哪开始。它只维护余额和补充速率，所以没有清零跳变；代价是它允许突发到 `capacity`，瞬时流量可以超过 `rate`。

| 方案 | 窗口边界 | 允许突发 | 每个用户存什么 |
|---|---|---|---|
| 固定窗口 | 交界处可能放行接近两倍 | 窗口开头可以 | 一个整数 |
| 滑动窗口 | 任意 60 秒内都不超限 | 最多到限额 | 时间戳列表或若干小格 |
| 令牌桶 | 连续补充，没有跳变 | 可以，上限是桶容量 | 余额、上次补充时间 |

## 被拒绝时回什么 {#reject-response}

限流命中后，返回 `429 Too Many Requests`，别用 `403` 或 `500`。`403` 会让客户端以为权限不够，`500` 会让它以为你崩了，两种都会引发错误的处理逻辑。

一个能用的响应长这样：

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 5
Content-Type: application/json

{"error": {"code": "rate_limited", "title": "请稍后重试"}}
```

`Retry-After` 可以是秒数，也可以是 HTTP 日期。它应该是"最早什么时候可能有令牌"，不是随手写个 60。令牌桶差 1 个令牌、速率是每秒 1 个，就写 1；写 0 等于告诉客户端立刻重试，拒绝就白做了。

响应体给机器一个稳定的 `code`，给人一句能懂的话。`X-RateLimit-Limit`、`X-RateLimit-Remaining` 这类头不是标准，但很常见；要暴露就写清单位是"次数"还是"秒"，别让客户端猜。

客户端收到 429，先看 `Retry-After`，再按指数退避加随机抖动重试。不要写 `while True: request()`——被限流的请求重试，只会把压力再放大一轮。

还有一件事比退避更重要：**重试前确认这个操作能不能重复执行。** 下单、扣款这类非幂等操作，要带幂等键；否则你以为是"重试一次"，下游可能已经执行过两次。限流只挡住入口，不保证操作只发生一次。

## 多台机器各算各的，限额就失效了 {#distributed}

进程里的字典和令牌桶，只属于那个进程。三台机器各跑一份"每分钟 100 次"的限流，总量就是 300 次；用户只要轮流落到三台机器上，就能绕过你在代码里写下的 100。

按 cookie 把用户粘在同一台机器上也不解决问题。单个用户确实只打一台，但三台机器的额度互不相干，整体限额仍然不存在；某台机器还可能被打满，另外两台闲着。

要的是全局限额，计数就得放到所有实例都能看到的地方：Redis、数据库，或者一个专门的限流服务。Redis 上的固定窗口伪代码：

```text
count = INCR rl:user:17:2026-10-25T12:34
if count == 1: EXPIRE key 60
if count > 100: reject
```

`INCR` 是原子的，但 `INCR` 和 `EXPIRE` 是两次调用。如果进程在两者之间挂掉，key 没有过期时间，这个用户会被永久限流。用 Lua 把两步绑成一个原子操作，或者先 `SET key 0 EX 60 NX` 再 `INCR`，都能避开这个缺口。

令牌桶放进 Redis 也一样：读余额、按时间补充、扣减，这三步必须是一个原子操作，否则两个实例同时读到旧余额，各自扣一次，限额照样被突破。

进程内限流仍然有用，只是角色变了：它作为本地兜底保护，防止某个实例被瞬间打爆，连去 Redis 计数都来不及。本地上限可以比全局宽松，例如全局 100 次、三台机器各设 40 次；真正准确的判断交给共享存储。

## 四个容易想反的地方 {#pitfalls}

**"限流就是防 DDoS。"** 应用层限流通常发生在 TCP 连接建立、请求解析之后。带宽型洪水在到达你的代码之前，就已经把出口和连接数占满了。限流能挡的是账号级滥用、失控的客户端、爬虫；大流量攻击要靠 CDN、WAF 或上游清洗，这些东西不在一个 Python 装饰器里。

**"三台机器各限 100，总量就是 100。"** 是 300。每台机器只看得见自己，除非它们共享计数。这个错误在扩容时最容易出现：原来单机限得好好的，加到三台，实际额度悄悄翻了三倍。

**"排队比拒绝好，队列开大一点就行。"** 无界队列会把过载从"立刻失败"变成"等很久再失败"。内存一直涨，客户端等到超时又重试，同一份工作被排了多次。队列要有界，且在排不下时直接返回 429；只有下游确实能消化、等待时间也能接受时，排队才是选项。

**"限额调得越小越安全。"** 正常的突发会被误杀，客户端重试进一步放大流量，真正需要服务的用户反而被挡。限额应该从下游容量倒推：数据库连接池能同时处理多少、第三方接口每分钟给多少配额。上线后盯三个数：429 的比例、被拒绝请求的等待时间、下游是否仍然接近饱和。

判断标准不复杂：**先找到最先被打满的那份资源，按它定限额；拒绝时告诉客户端什么时候再来；多实例部署时，把计数放到进程外。**

限流也不是唯一的过载手段：能降级的查询先降级，能异步的任务放进有界队列，能缓存的别每次都打下游。限流适合挡住"本来就不该发生的重复请求"，不适合拿来掩盖一个容量不足的下游。

## 练习：令牌、窗口与多实例 {#self-check}

**第 1 题**：桶容量 5，补充速率每秒 2 个，初始为空。到第 1.2 秒时连来两个请求，都能过吗？第三个呢？

> **答案**
>
> 能过两个。1.2 秒补进 `1.2 × 2 = 2.4` 个令牌，扣掉两次剩 0.4 个，第三个不够。
>
> 用代码验证：
>
> ```python
> tokens = min(5, 1.2 * 2)
> print(round(tokens, 1))          # 2.4
> print(round(tokens - 2, 1))      # 0.4
> ```

**第 2 题**：固定窗口限额 100 次/分钟。客户端在 12:00:59 发了 100 次，在 12:01:00 又发了 100 次。这两秒里实际放行了多少次？换成令牌桶，怎么避免？

> **答案**
>
> 200 次。12:00 窗口和 12:01 窗口各算各的，交界处没有任何"过去 60 秒"的记忆。
>
> 令牌桶的容量设成 100、速率设成 100/60，长期平均被压到每分钟 100 次，任意短时间的突发最多也只有 100 个令牌可用。要严格限制任意 60 秒窗口内的总数，用滑动窗口。

**第 3 题**：服务扩到三台机器，每台代码里都写了"每用户每分钟 100 次"。现在真正的限额是多少？要改成全局 100，怎么做？

> **答案**
>
> 每个用户最多能打到 300 次，而且取决于负载均衡把他分到几台。
>
> 把计数放进共享存储，例如 Redis 的 `INCR` + 过期时间，或 Lua 脚本实现的令牌桶。三台机器读写同一个 key，才共享同一份额度。
>
> 本地的 100 次可以保留，但要明白它只是单机保护，不构成全局限额。想更严格一点，可以把全局预算拆小：全局 100，每台本地设 40，防止某台实例在共享存储变慢时被打穿。
